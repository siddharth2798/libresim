# libresim: setup, running and usage

libresim is a local Cessna 172 flight simulator (with an optional A320) for the Mumbai–Pune region and the Mumbai–Kochi corridor. This file is the user manual and the developer reference. Design and roadmap: `PLAN.md`. Coding conventions: `CLAUDE.md`.

- **Players:** Quick start, section 4 (running, keys, screens), section 7 (troubleshooting).
- **Developers:** sections 2 and 3 (data pipeline), the aircraft data sections, tests, 4b (packages).

## Quick start

**Without a terminal.** Double-click in the project folder:

- **Linux:** `Start libresim.desktop`. If the data is ready, the game opens (output in `data/run.log`). Otherwise a terminal runs `./run.sh` (asks before any `sudo` install) and starts the game when done. GNOME: right-click the file once and choose **Allow Launching**. COSMIC and KDE: just double-click (mark it trusted if asked).
- **macOS:** `Start libresim.command` (opens Terminal for the setup, then the game; if macOS blocks it, right-click, Open).
- Each launch adds **libresim** to the applications menu (`~/.local/share/applications/libresim.desktop`). `./launch.sh --register-only` adds only the menu entry.
- The launcher finds the game folder from its own location, else from `~/.config/libresim/root` (written on every launch).

**From a terminal.** One command installs what is missing, downloads the raw data, builds the game data and starts the game:

```bash
./run.sh                              # set up everything (a true first run takes hours), then fly
./run.sh --airport=VABB --stand       # game options pass straight through (section 4)
./run.sh --dry-run                    # show the plan and what would run or be skipped, and why
```

Before anything is downloaded or built, `run.sh` prints a **plan**: the raw data still to fetch (size of each file and the total in GB; imagery and the corridor are estimates), the pipeline steps that will run with why and the usual time of each (from `data/run.log`, else a built-in table), and the expected total. It then asks `Continue? [y/N]` (`--yes` skips it); when nothing is stale it says "Everything is up to date" and goes straight on.

While it works you see `[3/17] file (84 MB)` and `downloaded 0.62 of 1.22 GB (51 %)` per download, `step 10: buildings, usually about 20 min, overall 35 %` per step, and every 15 s a `... step 10 running 2 min 30 s` line so a long silent step does not look stuck (`RUN_HEARTBEAT=secs` changes it). A true first run downloads about 2.5 GB and builds for hours (imagery 30-60 min, step 15 about 1 h, step 10 about 20 min); a second run starts the game in seconds.

A step runs only when its outputs are missing, an upstream step ran, or an input changed (stamps in `data/.stamps/`). Python scripts are compared by their code (`tools/code_hash.py`, hashes in `data/.stamps/<step>.hashes`), so editing a comment, a docstring or the formatting does not rebuild anything; raw data and json inputs are compared by file time. `tools/test_run_sh.sh` tests all of this in a scratch copy. Options: `--setup-only`, `--skip-data` (launch without touching data), `--region=mumbai_pune|all` (default `all` also fetches the Konkan-Kerala corridor), `--a320` (also fetch the A320 data and regenerate its json), `--force-step=NN` (re-run one pipeline step), `--yes` (answer yes to prompts), `--help`. Missing system packages (GDAL, python3-venv, curl, git, unzip) are detected for apt, dnf, pacman and Homebrew: the install command is printed and run with `sudo` only after you say yes. If Godot 4.7.2 is missing it offers to download it into `~/.local/bin`. Blender is not needed. Everything is logged to `data/run.log`.

**macOS:** `run.sh` needs bash 4+ and Homebrew GDAL: `brew install bash gdal python`. It re-runs itself under Homebrew's bash (`/opt/homebrew/bin/bash` on Apple Silicon, `/usr/local/bin/bash` on Intel) and builds the venv from Homebrew's `python3` (its site-packages hold GDAL's Python bindings).

Sections 2 and 3 describe the steps `run.sh` automates.

## 2. Getting the raw data (one time)

Everything goes in `data/raw/` (git-ignored). Sources: `tools/01_fetch_notes.md`. Run from the repo root.

```bash
# DEM: Copernicus GLO-30, 6 tiles (no account needed)
mkdir -p data/raw/dem && cd data/raw/dem
for t in N18_00_E072_00 N18_00_E073_00 N18_00_E074_00 N19_00_E072_00 N19_00_E073_00 N19_00_E074_00; do
  curl -fLO https://copernicus-dem-30m.s3.amazonaws.com/Copernicus_DSM_COG_10_${t}_DEM/Copernicus_DSM_COG_10_${t}_DEM.tif
done; cd -

# OpenStreetMap: western India (~220 MB)
mkdir -p data/raw/osm
curl -fL -o data/raw/osm/western-zone-latest.osm.pbf https://download.geofabrik.de/asia/india/western-zone-latest.osm.pbf

# OurAirports
mkdir -p data/raw/ourairports
for f in airports runways navaids airport-frequencies; do
  curl -fL -o data/raw/ourairports/$f.csv https://davidmegginson.github.io/ourairports-data/$f.csv
done

# JSBSim aircraft data (sparse clone: c172p + engines only)
git clone --depth 1 --filter=blob:none --sparse https://github.com/JSBSim-Team/jsbsim.git data/raw/jsbsim/src
git -C data/raw/jsbsim/src sparse-checkout set aircraft/c172p engine

# Satellite imagery: Sentinel-2 cloudless 2024 (EOX), reprojected to the world frame (~20-40 min, ~0.5 GB)
tools/01b_fetch_imagery.sh      # set LAYER=s2cloudless-2023_3857 to use a different year
tools/01c_fetch_outer_imagery.sh   # outer ring at 80 m (~490 x 490 km), ~15 min; re-run if it reports download errors (it resumes)

# Outer-ring elevation: Copernicus GLO-90 tiles 16-21 N, 70-76 E
mkdir -p data/raw/dem90 && cd data/raw/dem90
for lat in 16 17 18 19 20 21; do for lon in 70 71 72 73 74 75 76; do t=N${lat}_00_E0${lon}_00
  curl -fsLO https://copernicus-dem-90m.s3.amazonaws.com/Copernicus_DSM_COG_30_${t}_DEM/Copernicus_DSM_COG_30_${t}_DEM.tif || true  # open-sea tiles don't exist
done; done; cd -
```

### Corridor (Mumbai → Kochi)

```bash
tools/.venv/bin/python tools/01d_fetch_corridor.py all   # GLO-30 + GLO-90 + 20 m / 80 m imagery + southern-zone OSM; ~40 min, resumable
```

## 3. Building the game data

Run from the repo root, **in this order** (later steps read earlier outputs). `./run.sh` does this for you.

```bash
PY=tools/.venv/bin/python
$PY tools/05_airports_navaids.py   # -> data/processed/airports.json, navaids.json (both regions)
$PY tools/28_airways.py            # -> data/processed/airways.json (AAI eAIP ENR 3.1 and 3.2; network the first time)
$PY tools/04_osm_extract.py        # -> data/processed/osm/ (runways, roads, water, buildings), both regions; ~6.5 min; [--thin] = corridor density policy
$PY tools/02_dem_tiles.py          # -> terrain/h/ heightmaps, runways flattened; corridor ~2 min
$PY tools/03_imagery_tiles.py      # -> terrain/img/ BC1 .dds tiles (needs s2.tif; corridor: s2_corridor.vrt) ~15 s + 2 min
$PY tools/06_jsbsim_to_json.py     # [aircraft id, default c172] -> game/aircraft/<id>/aero.json, config.json (committed)
$PY tools/09_runways.py            # -> runways.json (merged runways + taxiways, runway surface from OurAirports, taxiway width_known; after 02, 04 and 05)
$PY tools/10_buildings.py          # -> buildings/ 3D meshes in the BLD2 layout (after 02, 04); ~2.5 min on 8 processes, 364 MB + 79 MB collision.
                                   #   Roofs come from s2.tif / s2_corridor.vrt; tiles without heights are skipped; geometry in tools/building_geom.py
$PY tools/11_landclass.py          # -> terrain/lc/ water and tree-density masks (after 02-04); ~30 s + 2 min
$PY tools/12_outer.py              # -> terrain levels 3-6 over ~980 x 1475 km to Kochi (real 90 m data, filled beyond); ~7 min
$PY tools/19_worldcover.py         # -> terrain/wc/ ESA WorldCover 2021 v200 class tiles (CC BY 4.0), one per lc tile (after 11 and 12).
                                   #   First run needs network (GDAL /vsicurl/ reads of public COG tiles, no account, ~150 MB into data/raw/worldcover/,
                                   #   resumable; --download-only only fetches). Codes: 0 nodata, 1 tree, 2 shrub, 3 grass, 4 crop, 5 built-up, 6 bare,
                                   #   7 snow, 8 water, 9 wetland, 10 mangrove, 11 moss. 1758 tiles, 76 MB, ~1 min. --force rebuilds.
                                   #   The terrain shader varies the ground per class; without wc/ the ground looks as before. Credit: CREDITS.md
$PY tools/13_airport_ops.py        # -> airport_ops.json: stands, gates, jetbridges, hold points, taxi graph; ~35 s
                                   #   stand_geom / stand_links / stand_remote / airport_stands.py derive airliner stands where OSM maps jet bridges but
                                   #   no stands (Kochi, Kannur). ./run.sh re-runs 13 when 13_airport_ops.py, a stand_*.py or
                                   #   airport_stands.py changes (or --force-step=13).
                                   #   jetway_net.py splits each OSM jet-bridge network into movable bridges and fixed links ("jetlinks") that run 2 m
                                   #   into the terminal wall; `python tools/jetway_net.py` re-does only that, in place.
                                   #   stand_aim.py then points an OSM jetbridge stand at the bridge that can meet its left door
                                   #   (slides a short lead-in, or turns the heading) and drops a duplicate of that lead-in.
                                   #   Check: godot --headless --path game res://tests/debug_jetway_audit.tscn
$PY tools/14_ils.py                # -> ils.json: SIMULATED ILS for runways >= 2000 m (after 09)
$PY tools/15_terminals.py          # -> terminals/<ICAO>.json terminal footprints (VABB, VAPO, VOCI via cached Overpass, plus every airport in
                                   #   tools/ref/terminals_reference.json); ~15 min
$PY tools/16_terminal_models.py    # -> terminals/<ICAO>.glb landmark terminal models + landmarks.json (after 17); then re-run 10_buildings.py
$PY tools/20_roads_rivers.py       # -> terrain/ro/0/ road and river masks (after 04, 11, 12, 17). OSM highway and waterway lines of both regions
                                   #   (first run ~5 min, cached in osm/ways.npz by tools/ways_extract.py), one PNG per level-0 tile: 1920 x 1920,
                                   #   4 m texels, two channels = signed distance to the ribbon edge (0.16 m steps within 4 m) and ribbon class.
                                   #   Roads stop at water (bridges stay), aprons, runways, taxiways; minor roads and waterways stop at aerodrome
                                   #   fences. 2213 tiles, 373 MB, ~7-11 min. --force rebuilds, --only tx_ty,...
$PY tools/21_shore.py              # -> terrain/sd/ shore distance (signed m, +127 m deep side) and openness per water land-class tile;
                                   #   1564 tiles, 58 MB, ~2 min. Drives shore foam, shoal colour, calmer backwaters
$PY tools/27_pavement.py --force   # -> terrain/pv/0/ airport pavement masks (after 04, 09, 13, 17): 38 PNGs, 1920 x 1920 RGBA, 4 m texels:
                                   #   edge distance, stand lead-in offset, slab direction, concrete / asphalt + stand wear. OSM aeroway areas
                                   #   cached in osm/aeroway_areas.json (--refresh-osm). ~1.5 min
$PY tools/26_terrain_textures.py   # only to change the set (output is in git): CC0 ambientCG ground textures -> game/world/textures/terrain/
                                   #   detail_mod.webp + detail_nrm.webp (11-layer arrays) + SOURCES.md; downloads into data/raw/textures once
$PY tools/17_airport_fixups.py     # patches terrain h/lc levels 0-2 in place, both regions (after 02, 09, 11, 12, 13, 15): levelled sites
                                   #   (VANM 8 m, VOKN, VOSR) without water / trees, taxiway ground smoothed, apron ground levelled
                                   #   (tools/apron_flatten.py: stands, gates, apron polygons, taxilanes and a margin round terminals / hangars lose
                                   #   the DSM's roofs, walls and parked aircraft; 30 m blend, all three LODs), no water on paving, no trees inside
                                   #   airports. Re-runnable (starts from the saved originals), ~3 min. Then re-run 09, 14, 16 and 10.
                                   #   ./run.sh order: ... 11 12 13 15 17 09 14 16 10
$PY tools/apron_roughness.py       # optional QA: stand-area relief, apron polygon std, terminal base height per airport

# Aircraft 3D models (FlightGear c172p, GPL), committed as .glb; only to regenerate:
blender -b --factory-startup --python tools/blender/convert_c172p.py            # exterior.glb
blender -b --factory-startup --python tools/blender/convert_c172p_interior.py   # interior.glb
# fgdata jetway: blender -b --factory-startup --python tools/blender/convert_ac.py -- <in.ac> <out.glb>
$PY tools/07_preview.py 1          # -> preview_L1.png (sanity check)
$PY tools/08_jsbsim_reference.py   # optional: standalone JSBSim climb numbers
$PY tools/18_compare_fdm.py        # optional: 11 scripted manoeuvres in our FDM and JSBSim c172p; PNG plots + metrics.md in /tmp/fdm_compare (docs/FDM-VS-FLIGHTGEAR.md)
```

Notes:
- **World frame:** local Transverse Mercator centred at 18.75N 73.40E, so map metres are game ENU metres (x east, y north). Juhu ≈ (-59540, 38628), VABB ≈ (-55997, 37576), VAPO ≈ (54856, -18505).
- **Regions:** 02, 03 and 11 take `--region mumbai_pune|konkan_kerala|all` (default all) and `--workers N`. `mumbai_pune` writes `terrain/meta.json` (levels 0-4; 12_outer replaces 3+). `konkan_kerala` writes `terrain/meta_konkan_kerala.json` (levels 0-2, tiles `[min, max, flags]`, flags bit 0 = img, bit 1 = lc; level-0 corridor tiles have neither and borrow from their level-1 parent). Corridor tiles that border Mumbai-Pune tiles are stitched to their edges; Mumbai-Pune tiles are never written by the corridor run. Corridor flattening uses runways.json (09), then OSM runways, then OurAirports ends: after a fresh 09 re-run 02/03/11 for the corridor.
- 03 skips existing img tiles: delete `terrain/img/` (or the corridor's `img/{1,2}/`) to rebuild them.
- `07_preview.py quicklook [level=2] [out.png]` mosaics every `meta*.json` at one level. `07_preview.py <level> x0 y0 x1 y1` zooms into a box, e.g. `07_preview.py 0 -62000 35000 -52000 41000` shows the Mumbai airports.
- To change the region or tile layout, edit `tools/common.py` and re-run 02-03.
- Delete `data/processed/` at any time; the scripts regenerate it.

### A320 data (optional, `./run.sh --a320`)

The A320 flight model comes from the FlightGear "A320-family" JSBSim files (licence **GPL-2.0-only**: `third_party/a320-family/`, `docs/LICENSING.md`). `data/raw/fg/a320` is untrusted data: it is decoded, never executed.

```bash
tools/22_a320_fetch.sh              # sparse checkout of FDE/ Engines/ Systems/ at the pinned commit (~2.5 MB); --force re-fetches
$PY tools/06_jsbsim_to_json.py a320 # -> game/aircraft/a320/{aero,config}.json (committed; c172 json untouched)
$PY tools/test_jsb_convert.py       # converter tests (c172 json must stay byte-identical)
$PY tools/23_a320_reference.py      # JSBSim oracle run -> tools/a320_reference.json + tools/ref/*.csv (a few minutes)
```

`./run.sh --a320` runs the first two (fetch is skipped at the pinned commit; json step 06a re-runs only when the converter or the clone changed). It does not download an aircraft pack. The withdrawable archive is built locally: `tools/package/make_pack.sh [version]` writes `build/libresim-a320-<version>.tar.gz` (default `0.1.0-dev`). `--list` prints the paths and writes nothing. The archive holds `game/aircraft/a320/`, the upstream licence files from `third_party/a320-family/`, and a pack `LICENSE`, `README.copyright.md`, `NOTICE` and `SOURCE-OFFER.txt` (`tools/package/a320_pack/`). It does not hold the C172 or `data/processed`. `tools/package/test_make_pack.sh` checks that list. The base game stays GPL-2.0-or-later; a distribution that includes this archive is GPL-2.0-only as a whole.

The converter makes three deliberate changes to the upstream data (its SPECS entry): `thrust_pos_m` puts the thrust on the model's engine centrelines (y ±5.63 m instead of ±2.8775 m), `rudder_k` (3) scales the rudder terms so an engine failure at V2 stays controllable, and `clmax` (`tools/jsb_clmax.py`: an extra lift term, per flap detent a `shift_deg` and `clmax_k`) raises CLmax so the 1 g stall speeds match the FMGC table (its alpha limits are in `fdm/fbw_params.gd`). The oracle run keeps the upstream data. Why: `docs/A320-STATUS.md`, `tests/test_a320_engine_out.gd`, `tests/test_fdm_a320_stall.gd`.

`23_a320_reference.py` flies the real A320 (FBW, FADEC, engines) headless in the JSBSim python package: trims, alpha limits, takeoff roll, climbs, FBW step responses, thrust formula. It is the tuning oracle for the hand-written control laws (`--only trim,stall,takeoff,climb,steps,thrust` selects parts). The first run builds `data/raw/fg/a320_root` (symlinks to the clone plus a stub system for ~700 FlightGear-side properties, ~3 min, cached). Details and the property bridge: `tools/A320_DATA_NOTES.md`.

### A320 model (optional)

The exterior and flight deck are converted from the FlightGear A320-family models (GPL-2.0-only; credits and change log in `third_party/a320-family/SOURCE.md`). Needs Blender 5.x (tested 5.2.3 LTS, run headless, not on PATH). No add-on: `tools/blender/ac3d_parse.py` reads the AC3D files.

```bash
tools/24_a320_models_fetch.sh                       # adds Models/ (~87 MB) to data/raw/fg/a320; run tools/22_a320_fetch.sh first
$PY -I tools/24_a320_textures.py                    # cleaned textures -> data/processed/a320/tex (white livery, no registration / logos)
B=/Applications/Blender.app/Contents/MacOS/Blender
$B -b --factory-startup --python tools/blender/convert_a320.py          # -> game/aircraft/a320/models/exterior.glb (+ exterior_pivots.json)
$B -b --factory-startup --python tools/blender/convert_a320_cockpit.py  # -> models/interior.glb (+ interior_info.json: eye, display rectangles; interior_pivots.json: moving controls)
$PY -I tools/24_a320_sections.py                    # -> game/aircraft/a320/model_sections.json (draft model / cockpit / lights / registration / cameras)
godot --path game res://tests/debug_a320_model.tscn --audio-driver Dummy -- --out=<dir> --pose=clean|down|spoil   # screenshots + pivot / triangle check
```

Budgets: exterior 75.7k triangles (71.9k plus probes, antennas, wicks, the APU exhaust, a drain mast, 48-side inlet lips, gear-door hinges, spinners and fan-blur discs), 12 materials, 4096 px fuselage atlas (for the registration), 2048 px rest and a 2048 px occlusion map; flight deck 95.9k triangles (94.6k plus two seats, a jump seat and the rear door, whose side panels follow the roof inside the skin), 29 materials (the panel set plus one copy per keyed annunciator), <= 2048 px, plus the same occlusion map. Shading (roughness, clearcoat, occlusion, panel-line normals, night cabin glow, exhaust stain, legend backlight, fan-blur opacity) is `aircraft/common/material_finish.gd` and `aircraft/common/fan_blur.gd`. glb origin = JSBSim structural origin (`model.origin_m` `[0,0,0]`). `model_sections.json` is a draft: its `_needs` list names the small `aircraft_model.gd` / `registration_paint.gd` extensions the pivots need (extra drives, piecewise `map`, `rotate`).

## 4. Running the simulator

```bash
cd game
~/.local/bin/godot --path .          # run the game
~/.local/bin/godot -e --path .       # open the Godot editor
```

The first run imports the project (a few seconds). The data is read from `../data/processed`, so build it first (section 3).

### Start screen

The logo splash shows first, then the home screen with two cards: **Free flight** and **Training**. Click one, or press **1** / **2** (or Left / Right) and **Enter**; the last choice is focused. Links below open **Saved flights**, **Controls** and **Options**; **Handbook**, **Credits** and **Quit** are in the top bar. Tab and arrows reach everything. **◀ Back** or **Esc** returns to home.
- **Fly again (R)** (Free flight card) starts your last Free-flight setup (`user://last_flight.json`) after the same check as **Fly now**. Not shown when the save is missing or damaged.
- **Continue: <lesson> (C)** (Training card) starts the lesson after the last one you flew, with full guidance. The card lists every lesson's stars (`user://training.json`). Not shown before the first or after the last lesson.

**Free flight** has a left rail: Aircraft → Livery (optional) → Airport & start → Route (optional) → Weather & time → Failures (optional) → Recording (optional). Aircraft is first because the airport page depends on it (air-start values, runway-length check and stands follow the aircraft). Livery is the paint step; Next skips it.
- Each entry shows its live value (e.g. `VABB · stand 12`) and a mark: green circle = ready, amber triangle = look at it, red triangle = problem, hollow ring = optional, nothing chosen. Hover for the reason. Problems are also listed under the steps as buttons that jump to the step.
- **Next ▶** moves on, **◀ Back** goes back (first step: home). The filled **Fly now ▶** in the bottom bar starts the flight from any step; it is amber **Fly anyway ▶** when the setup has a problem. The bar also shows the setup as chips (each jumps to its step).
- Keys: **1**–**7** jump to a step (not while typing), **Page Up / Page Down** step, **Ctrl+Enter** flies, **Esc** goes back one step. The last setup is saved (`user://last_flight.json`).
- Hover tips explain things. "More weather" and aircraft "Details" toggles keep their state for the session.

**"Fly anyway?"** Fly asks (never blocks) when the setup is over MTOW (`mtow_kg`), the CG is outside the envelope (`cg_envelope`), the runway is shorter than the aircraft's minimum (runway starts only), the tailwind is above 5 kt, or the crosswind is above the aircraft's limit (C172 15 kt, A320 33 kt). Wind checks apply to runway and air starts, not stand starts; gusts do not count. Visibility under 1.6 km is only a warning. **Go back** has the focus (Esc too). Lessons and saved flights skip the check.

1. **Aircraft**
   - Every `game/aircraft/<id>/aircraft.json` is listed with name, category and three key figures. **Full specification** shows the description and every specification row.
   - **Registration** is the call sign painted on the tail and used on the radio. Untouched, it follows the aircraft (C172 VT-LBR, A320 VT-ZZA). A typed one (3 to 7 letters or digits, one optional dash after the first one or two characters, e.g. `VT-ABC`, `N172SP`) stays when you change aircraft and is saved with the setup; `--callsign=VT-ABC` sets it too. An airliner is still called by its airline name on the radio ("Skyline 123"). A change shows at the next flight start. The same field is in Options → Radio / ATC.
   - Fuel and loads: one slider each. Payload changes mass, CG and performance. A badge (Within limits / Over MTOW / CG out of limits), a weight bar and a red message give the same text as the rail mark. The **weight & balance chart** shows the C172S normal and utility CG envelopes with the takeoff and landing points (landing assumes 5 gal per tank) and turns red when overweight or out of CG limits. An aft CG makes pitch light and less stable.
2. **Airport & start**
   - **Search:** type an ICAO code, part of a name or a city (`vabb`, `shivaji`, `calicut`; every word must match). Up / Down, Enter, Esc. Airports too short for the aircraft are dimmed.
   - **Diagram:** north-up runways, taxiways and stands with an arrow at your start. Click a runway end (or the strip: the nearer end) or a stand dot to pick it.
   - **Start at:**
     - **Runway:** the chosen end, engine running. One chip per end shows length and wind (`head 8 · cross 3 kt`; red when Fly would ask; `· short` when too short). Tick "cold & dark" to start with everything off.
     - **Stand & gate:** a stand from OSM (jetbridge gate, remote bay or GA parking). Stand starts are **always cold & dark with the parking brake set**.
     - **In the air:** height above the field and distance on final. They start at the aircraft's defaults, a landing start level a little under the 3° path (C172: 900 ft, 3 nm, 70 KIAS, flaps 30; A320: 2,200 ft, 7 nm, 160 KIAS, gear down, CONF 2) and follow the aircraft until you edit one (**Default** goes back). The speed has no control: it follows the aircraft unless `--air-kt` or a lesson sets it, and is clamped to 1.2 × `limits.vs1_kias` .. 0.9 × `limits.vne_kias` (C172 57.6 to 146.7 KIAS), or from 1.2 × `limits.vs0_kias` when the aircraft's own start has flaps out (A320 131 KIAS), with a log warning (`AirStart.spawn`).
   - **Stand names:** a real OSM ref is kept; a stand without one gets **Gate n** (jetbridge) or **Bay n**, numbered west to east, then south to north, skipping numbers real refs use; a repeated ref becomes `ref (2)`. "near Terminal 1" names the nearest terminal within 2.5 km. Lists: gates first for an airliner, bays first for the C172, GA tie-downs first for a light aircraft; then natural order (Bay 2 before Bay 10).
3. **Route** (optional): the waypoints you want to fly, from the Airport step's start to a destination. Skip it and the flight has no route (direct-to on the N map still works).
   - **From** is the Airport step's airport and start (`VABB 27`, `VABB · stand`, `VABB · in the air`). **To** is an airport search; the **arrival runway** chips (Any, or one end) add a final fix 8 nm out. **Cruise ft** (500 to 41,000) is the altitude new waypoints get; waypoints still at the old cruise follow a change. Default 4,500 ft, or FL240 for an aircraft that cruises at 250 kt or more.
   - **Auto-route:** **Direct** (no waypoints), **VOR to VOR** (hops between VOR / NDB stations, legs up to 120 nm, 200 nm where stations are sparse; short trips stay direct) or **Airways** (the shortest path over the published AAI airways, joined and left within 60 nm of the airports, one-way airways respected; fixes within 3 nm of either airport are left out). An amber line explains when a route can't be built (no destination, no airway near an airport); the route is then unchanged. **Clear** removes everything.
   - **Text box:** shows the route (`VABB BBB NMB WPT01 VAPO`). Type one and press Enter: idents separated by spaces or `/`, `DCT` ignored, an airway between two of its fixes expanded (`VABB DCT PAPRI W15 GOA VAPO`). An error keeps the old route. Free waypoints can't be typed.
   - **Map:** satellite imagery (dimmed) with airports, VOR / NDB, airway fixes and airways (shown when zoomed in), the departure (green ring), destination and the magenta route with course, distance and time per leg. **Click** an airport, VOR, NDB or fix to add it before the destination; **click empty map** for a free waypoint (`WPT01`, `WPT02`, ...); **Shift+click** an airport to make it the destination; **click a waypoint** to select it; **drag a waypoint** to move it (dropped on a point it becomes that point, elsewhere a free waypoint; the altitude stays); **drag the middle of a leg** to insert a waypoint; **right-click** a waypoint removes it. Wheel or + / − zoom, drag empty map or arrow keys pan, **F** / **Fit** shows the whole route.
   - **Nav log:** one row per leg: TO, magnetic course, distance, time at the aircraft's cruise speed (the "Cruise" KTAS in its specification: C172 124 kt, A320 450 kt), running total and an altitude box per waypoint, with ▲ ▼ × to reorder or delete. The last line is the total distance and time in still air.
   - **Fuel** (under the total): `Fuel  Trip 5 gal + reserve 3 gal · on board 34 gal`. Trip = distance ÷ cruise speed × cruise burn (`payload.cruise_gph`, C172 9 gal/h; A320 `payload.cruise_kgh` 2,500 kg/h), reserve = `payload.reserve_gal` (C172 3 gal) or `reserve_kg` (A320 1,800 kg; 30 min at cruise burn when an aircraft gives none), on board = the Aircraft step's fuel, all tanks. Red when on board is less than trip + reserve, amber when you would land with less than twice the reserve. An "In the air" start on leg N counts from leg N. Still air, no climb allowance.
   - **Vertical profile** (the strip under the map): the ground along the route (sampled every 0.5 nm from the terrain data, the coarse outer tiles where there is no fine one) and the planned altitude of each leg (the leg into a waypoint flies its altitude, the leg into the destination the last waypoint's), the departure and destination elevations as dots, waypoint ticks, and a caption: highest ground and the lowest clearance with its leg. Where a leg is less than 1,000 ft above the ground the line and the ground under it turn red. The first and last 2 nm (take-off and landing) are drawn but not judged.
   - **Plans** (the buttons under the nav log): **Save plan…** asks for a name (suggested `VABB to VAPO`; the same name replaces that plan) and keeps the departure, the route and its altitudes in `user://plans/<name>.json`. **Load plan…** lists the saved plans newest first (departure → destination, waypoints, date) with Load and Delete; a plan that starts at another airport also sets the departure (runway and stand cleared) and the note line says so. **Import .PLN…** opens a Microsoft Flight Simulator / Little Navmap flight plan (MSFS 2020 / 2024, FSX and P3D AceXML `.pln`): the departure must be an airport libresim has (else an error); idents the nav data knows become those points (when within 10 nm of the file's position), other points inside the world become free waypoints where the file puts them, points outside the world are left out (the note names them); altitudes from each waypoint's position line, else the plan's cruising altitude. **Export .PLN…** writes the route for MSFS / Little Navmap (VFR, or IFR on airways or at FL180 and above; your free waypoints as User waypoints). Both use the system's file dialog.
   - **Start** (only with an "In the air" start): **On final** (the Airport step's numbers) or **On leg N: A → B**: you start 2 nm past A (mid-leg on a short leg), heading along the leg, at its altitude but at least 1,000 ft above the ground ahead, clean, at cruise speed (`start.air.cruise_kias`, else an airliner's managed cruise speed, else 85 % of Vno; at most 250 kt below 10,000 ft and Mach 0.78; C172 110 KIAS, A320 280 KIAS above 10,000 ft). An airliner starts with the thrust levers in CL, A/THR armed and active, and managed speed, so engaging the autopilot flies the route. The Airport rail then reads `VABB · in the air, route leg 2`.
   - **In the flight:** the route is the GPS route (N map, mini-map, A320 F-PLN and ND), flown waypoint by waypoint (the next one within 1 nm). A runway start on a chosen runway flies its departure fix first (`VABB27D`). On the A320 the MCDU INIT page is filled (FROM/TO with every waypoint, DEP / ARR RWY, CRZ FL = the highest leg altitude), the FCU altitude is set to it with managed vertical, and NAV (managed heading) is selected as filing INIT does, so the autopilot flies the route. ATC's clearance names your destination. The C172 has no autopilot: follow the GPS line. Saved flights keep the route; F5 starts it again. Lessons never use it.
   - **Changing it in flight:** on the moving map (**N**) press **Edit route** (the button turns into "Editing route", the map gets a magenta frame and the title starts with EDIT ROUTE). The map then shows the route ahead, from the aircraft (the start of the active leg) to the destination, and takes the Route step's gestures: **click** adds a point before the destination (an airport, navaid or fix under the cursor, else a free waypoint), **Shift+click** an airport makes it the destination, **drag a waypoint** moves it, **drag a leg** (also the one from the aircraft) adds a point on it, **right-click** removes one, dragging empty map pans, the wheel zooms. Each edit is flown at once. Closing the map leaves edit mode. Or **Esc → Edit route**: the Route step's map, nav log (from `PPOS`, the present position), fuel line (the fuel on board now), vertical profile, destination, arrival runway, cruise altitude, auto-route and typed route, on the route ahead; nothing changes until **Apply and resume**; **Cancel** or Esc drops the edits. Not on that page: the departure, plans and .PLN, the start leg. When the route changes the GPS keeps its active waypoint while it is still the first point ahead; when that point was removed or moved, or a point was put on the leg to it, the first point ahead becomes active. Waypoints already flown stay in the plan (a free waypoint added later gets a new `WPTnn` name), so the next start, F5 and saved flights fly the edited route. ATC's destination, the mini-map and ND follow; on the A320 the F-PLN is the new route, INIT FROM/TO, ARR RWY and CRZ FL (the edited cruise altitude, or a higher leg altitude) are re-filled, DEP RWY stays, NAV keeps flying it, and the FCU altitude and managed modes are left alone. On the pause page the aircraft symbol marks the start (no departure ring).
   - Checks on the rail and the chip: **red** (Fly then asks "Fly anyway?"): a leg planned below the ground, or fuel on board less than trip + reserve. **Amber** (never blocking): a leg less than 1,000 ft above the ground, landing with less than twice the reserve, the destination's runway (the arrival runway, else its longest) shorter than the aircraft needs (`ground.min_runway_m`, the Airport step's rule), destination not in the nav data, a waypoint more than 600 nm away, a start leg the route no longer has.
4. **Weather & time**
   - **Presets:** Clear, Fair, Scattered, Broken (passing showers), Overcast (drizzle), Winter haze, Monsoon (heavy rain under a low deck, lightning). A line says what the preset is, or "Custom".
   - **Time:** presets, the **day strip** and a "Time (IST)" slider. The strip is a 24 h bar (night, twilight, day) with sunrise and sunset above it; click or drag sets quarter hours (focused: Left / Right 15 min, Page Up / Page Down 1 h). **Dawn** and **Dusk** are the real sunrise and sunset for the **Month** (mid-February 07:10 and 18:40 IST; June about 06:00 and 19:15). One sky serves the whole map (18.75 N, 73.4 E): times depend on the date, not the airport.
   - **Wind:** presets, "Wind from" and "Wind speed" sliders, the **wind dial** and "90° crosswind". The dial is a compass with the chosen runway and an arrow showing where the wind blows; click or drag sets the direction in 10° steps (focused: Left / Up, Right / Down). The head / crosswind line turns amber from 80 % of the crosswind limit or with more than 2 kt tailwind, red above the limit or with tailwind above 5 kt (what Fly asks for). A stand start has no runway: the wind shows alone.
   - **More weather** (collapsed): cloud cover, base, visibility, rain, turbulence, thermals, storm cells, icing, gusts, QNH, temperature, clock rate, month.
5. **Failures** (optional)
   - Pick an area (left), switch a failure on and choose its trigger: **At start**, **After time** (min), **Altitude** (ft AGL) or **Airspeed** (kt). The **Armed** list (right) shows what you will get, each with a **×**; **Clear all scheduled failures** also turns random failures off. There are 26 failures; the areas come from the aircraft (the A320 also shows hydraulics, fire and more). C172:

     | Area | Failures |
     |---|---|
     | Engine | total, partial power/rough running, left and right magneto |
     | Fuel | left and right tank leak |
     | Electrical | alternator, battery |
     | Vacuum & gyros | vacuum pump, attitude gyro, heading gyro, turn coordinator |
     | Pitot-static | pitot blocked, static blocked |
     | Flight controls | flaps jammed, trim jammed, left and right brake |
     | Avionics | COM1, COM2, NAV1, NAV2, ADF, DME, transponder, GPS |

   - **Random failures:** how many, a time window (min) and which systems may fail. You are not told which are armed.
   - **Tell me when something fails** shows a notice; off, you diagnose from the instruments.
6. **Recording** (optional)
   - **Record this flight** records the session, picture and sound. **F8** starts / stops it in flight (a red ● REC shows time and size); `--record` turns it on.
   - Folder (default `recordings/` in the game folder; read-only installs (AppImage, .app) use `~/.local/share/godot/app_userdata/libresim/recordings`), resolution (720p, 1080p, native window), frame rate (24, 30, 60 fps). The options are only dimmed while recording is off: F8 still records with them.
   - Files are `libresim_<date>_<time>.mkv` (MJPEG + 16-bit PCM), written by the game, no extra software needed; they play in VLC and mpv. About 5 MB/s at 720p30. The file is a stream, so it stays playable if the game is killed. Frames are read back and encoded on worker threads, so the frame rate is barely affected.
   - **Convert to MP4:** with `ffmpeg` installed, a much smaller MP4 (H.264 + AAC) is made when recording stops.

**Controls** (home → Controls; in flight **J**, opens on the joystick tab): tabs **Keyboard**, **Joystick & gamepad**, **Other keys** (fixed hotkeys). **Controls for** (C172S / A320-family) lists the other aircraft's actions without changing your setup. **Search actions** (Ctrl+F / Cmd+F) filters by action name or bound key.
- **Keyboard:** click a slot (up to 3 keys per action, Shift / Ctrl / Alt allowed), press the new key. Esc cancels, Delete clears, conflicts show in orange, **Reset keys to defaults**. Keys match by physical position. Saved in `user://key_bindings.json`.
- **Ground operations** have their own section on the Keyboard and the Joystick & gamepad tabs (`ControlActions.GROUND`): taxi route (T), pushback (P), jet bridge retract / dock (Shift+J), door L1 (O), ground vehicles (U) on every aircraft, and on an aircraft with more doors (action group `doors`, A320) all passenger doors (Shift+O) and all cargo doors (Ctrl+O), worked apart, plus one row per door: R1, L2, R2, forward and aft cargo (no default key: bind them there). Pushback waits until the jet bridge is retracted and every passenger and cargo door is shut, and says which key does it (`world/pushback_checks.gd`); a bridge retracted for pushback docks again at the arrival gate. All are rebindable keys and joystick buttons; taxi route and pushback bump `controls/ground/taxi_req` / `push_req`, which `world/ground_ops.gd` watches (each press toggles). The F1 card lists them. Test: `tests/test_ramp_keys.gd`.
- **Joystick & gamepad:** connected devices are listed; hot-plug works. Each action has **Bind** (move an axis or press a button; Esc or 10 s cancels), clear, a live bar and **Tune** (invert; range: full, half for levers, trigger for toe brakes; deadzone; expo curve). Resets: gamepad = left stick roll/pitch, right stick X yaw, triggers toe brakes, LB/RB flaps, A brakes, X parking brake, Y/B views, D-pad trim and magnetos; joystick = X/Y roll/pitch, twist yaw, throttle axis. A bound axis takes over from the keyboard; unbound actions stay on the keyboard. Saved in `user://input_bindings.json`. The Thrustmaster Captain Pack has its own profile (below).

**Options** (home → Options; same pages in the pause screen) has seven tabs and saves at once (`user://options.cfg`, `user://audio.cfg`):
- **Sound:** volume and mute per bus (Master, Engine, Wind & environment, Cockpit, Radio, Menus).
- **Graphics:** preset (Low to Max), **Renderer, next start** (Mobile / Forward+; asks "Restart now?" and relaunches, see section 5) and the post-effect switches (section 5).
- **Display & units:** **UI size** (Auto, or 100 / 125 / 150 / 200 % of the system display scale; Auto keeps text, HUD and menus the same relative size from small windows to 4K and ultrawide; the 3D view always renders at full resolution; saved as `ui_scale`), units (stored for later; the C172 panel stays ft, kt, inHg).
- **Screen layout:** your own outside-view layout, the **Custom** entry in the Tab cycle. A 16:9 preview has a box for every shown piece and the flight-data bar: drag a box to move it, drag its corner or turn the wheel over it to resize (the shape is kept). A switch per piece shows or hides it (C172: six-pack, nav dials, mini-map, engine, radio stack, switch row; A320: PFD and ND, engine and systems displays, MCDU, mini-map, FCU), plus "Flight data bar at start" (`hud_at_start`). **Aircraft** picks whose layout you edit; **Reset to the default layout** goes back to the catalog. Changing anything selects Custom, and a flight under the pause screen follows at once. The bar's place and size apply in every layout and view. Storage: `user://ui.cfg` (`[layout_<aircraft>] pieces` = {id: {on, x, y, h}}, top-left and height as fractions of the screen; `[hud]` x (centre), y (top), scale; `[panel] layout_name`). The pieces are each aircraft's `panel.json` `pieces` catalog (label, items, default anchor and height, on). Code: `ui/screen_layout.gd` (data), `ui/menu/screen_layout_tab.gd`, `ui/menu/screen_layout_preview.gd`; Props `ui/layout_rev` makes the panel overlay and the HUD re-read it. Test `tests/test_screen_layout.gd`.
- **Flight controls:** yoke keys, input smoothing, auto-coordination ("Control feel").
- **Radio / ATC:** call sign, **radio assist** (default on), ATC voice.
- **Training aids:** callouts (K) and "Speak them". **Voice** ("Speak them", "ATC voice"; both off by default) uses the system text-to-speech and probes the system once when switched on (about 0.5 s); with no voice found it stays silent with a note. Linux needs `speech-dispatcher` and a voice: `sudo apt install speech-dispatcher espeak-ng` (Fedora `sudo dnf install ...`, Arch `sudo pacman -S ...`), then restart. Windows and macOS use built-in voices. Code: `core/speech_service.gd` (one door for callouts and ATC; `tests/test_speech.gd`). A run started with `--audio-driver Dummy` (muted tests) never speaks: the system voice bypasses the Godot audio driver, so `core/speech_backend.gd` checks the driver itself.

**Saved flights** (home → Saved flights): cards with picture, name, airport, aircraft and date, newest first. **Fly from this save** (or double click / Enter) resumes exactly there. **Delete** asks first (**Yes, delete** / **Keep it**). Saves are in `user://saves/`. Make one with Esc → Save flight or F11.

**Training mode** (home → Training, or `--lesson=takeoff|cruise|landing[,full|light|off]`): three short lessons at Pune in calm, clear weather; your Free-flight setup is not changed. Any lesson can be started.

| Lesson | You practise |
|---|---|
| **Takeoff** | Full power, staying on the centreline, rotating at 55 kt, climbing at Vy (74 kt), reaching 500 ft |
| **Cruise** | Level flight, cruise power, trim, a 90° turn, a 500 ft climb and descent |
| **Landing** | Slowing down, flaps, the 3° glide path and centreline, the threshold, the flare, touchdown and roll-out |

The landing lesson starts 3 nm out (1,000 ft, 80 kt, flaps up, on the 3° path). Steps: **Slow down** (about 1,700 RPM, 58 to 78 kt), **Flaps and trim** (flaps 20° with `]` or `F7` twice, about 65 kt; `End` nose-up trim, `Home` nose-down), **Fly the glide path** (within 1.5°, stable by 0.8 nm out), **Cross the threshold** (about 60 kt), **Flare and touch down**, **Roll out** (brake with `B` to 10 kt or less).
- A **lesson card** (left) lists steps, the instruction and a hint, and ticks steps off. **Live gauges** show your value against target and tolerance (green inside, amber near, red far). **3D markers:** dashed centreline, glide-path rings (cyan ahead, yellow next, green flown, red missed), an aim-point box, a beacon in the cruise lesson. **Coach messages** ("Rotate now!", "High. Reduce power, lower the nose") and optional speech; callouts are always on in a lesson.
- **Help level:** *Full guidance*, *Hints only* (card, hints, callouts) or *Minimal* (step list only).
- **Result:** 1–3 stars from the graded numbers (centreline error, rotation and climb speed, sink rate, touchdown point, ...), with **Try again**, **Next lesson**, **Keep flying**, **Menu**.
- Steps are in order but not strict: if you already meet a later step's conditions, earlier ones tick for you.
- **A lesson never leaves you stuck:** if you can no longer finish it (touched down or left the runway too early, far too low or high, floated off the end, settled back after rotating, flew into the ground, crashed) it ends with a "not completed" card (what happened, in which step, what to work on). **Try again** and **F5** put the aircraft back at the lesson start from any state.
- Lessons are data in `game/training/lessons.json`: steps (`any_order` for tolerant ones), conditions, gauges, grades, `abort` rules. `--air-kt=` sets the IAS of an airborne start.

**In flight:**
- **Esc** opens the pause screen: the flight stops behind a blurred backdrop, and the engine, wind, cockpit, radio and spoken callouts go silent until you resume (menu volume is left as you set it; this mute is not saved). Resuming is instant. The left column: **Resume flight**, **Options**, **Weather & time** (F10), **Controls & keys** (J), **Save / Load flight** (F11), **Failures** (F9), **Checklists** (F2), **Instant replay** (R), **Restart flight** (F5), **Quit to main menu**, **Quit game**; the page shows on the right. ↑ ↓ move down the list, ← → cross between list and page, **Enter** selects, the mouse works. **Esc** backs out one level (text field, page, resume). Other keys are ignored while paused; a pad pause button works like Esc. Restart and the two Quit entries need a second click ("Click again to confirm", cancelled by Esc or after 3 s).
- **Save / load:** Esc → Save / Load flight, **F11** quick-save, **Shift+F11** quick-load. A save keeps position, motion, engine state, fuel, damage, switches, radios, failures, weather and time (`user://saves/`).
- **Replay (R):** the last 10 minutes from any camera. **Space** plays / pauses, **← / →** seek ±5 s, **[ / ]** speed 0.25x–4x, the timeline can be scrubbed. **Take control** resumes flying from that moment with its exact speed and attitude; **Exit replay** returns to where you were.
- **F9** failures panel: every system OK, FAILED or armed; fail or repair any live; pending random failures.
- **Notification cards** (top centre): failures, damage, the landing debrief. Blue info, amber caution, red warning; repeats merge ("×3"), at most 3 show, they fade in seconds. STALL is a pulsing banner; a bottom hint says when the engine stopped.
- **Crash card:** dims the scene and gives the reason, impact numbers and damage, with **Restart** (F5), **Watch replay** (R) or **New flight**.
- **Loaders:** opening a flight or a lesson, flying a saved flight, and returning to the menu (pause, crash card, or the end of a lesson) play a short scenic film with the place name, a spinner and a percent over it (`ui/busy_overlay.gd`, `ui/loader_film.gd`). Each aircraft has its own two clips (`tests/showcase_film_scenes.gd`), chosen by how the flight starts: a stand start plays the gate at Kochi (A320 with its jet bridge docked, ramp vehicles out), everything else the Western Ghats (the Cochin approach clip was dropped); an A320 plays the A320 clips, anything else the Cessna's. The flying clips keep the aircraft flying while the camera drifts alongside, the gate clip orbits the parked aircraft; 5 s at 24 fps, 1600 x 900, Max preset, no depth of field, game time locked to the frame rate (`tools/shoot_loader_films.sh [scene ...]`, needs a visible window; frames in `ui/loader/<aircraft>_<place>/NNN.jpg`, about 15 MB a clip, shipped as the JPGs themselves: each `.import` is `importer="keep"`, written by the shoot script, and `ui/loader_frames.gd` decodes the next frame on a worker, so the 480 frames take 73 MB instead of 308 MB of lossless textures and the main thread no longer spends about 35 ms a frame decoding them). A menu load with no flight picks a clip at random. The data-attribution line sits on the film, the same line the flight keeps on screen. The film is up before the flight scene is shown and stays until the ground and the runway meshes are in (at most 12 s): the first terrain node, no finer terrain tile still pending (`TerrainQuadtree.pending_tiles`) and the airport builder done; the percent is half ground, half runways and never goes back. The window veil is anchored with its offsets (`set_anchors_and_offsets_preset`); with anchors alone it sat at 0 × 0 under its CanvasLayer and the film was never drawn. `tests/debug_loader.tscn` starts a flight through the start screen's Fly button in a window and saves a frame every `--every` s for `--secs` with what the loader waits on (`--out=<dir> --setup=<last_flight.json>`). **Fly loads in the background:** the flight scene and the chosen aircraft's models (exterior, interior, A320 doors) start loading on threads as soon as the Free flight setup opens or an aircraft is picked (`ui/scene_preload.gd`, `ResourceLoader.load_threaded_request`); after Fly the veil waits for them with the film playing and changes scene with the loaded scene, and `AircraftModel` / `Cockpit` take the loaded models (anything not preloaded or failed loads the normal way; headless runs load straight). **Airport corridors are registered lazily** (`world/corridor_book.gd`, `corridor_plan.gd`): planning the pushback swing of all 961 stands at 44 airports took about 3 s of every load. Now the start airport is planned on a worker while the flight scene builds and is in before the first physics step; any airport within 2 km of the aircraft is registered at once (a situation load or another jump too), airports within 15 km of the aircraft or camera are planned on a worker, and the airport lights wait for an airport's corridors before placing its masts. Positions are world ENU, so the floating origin does not matter. A small wait (painting a livery, reading the weather) keeps the plain veil. Live weather cycles dots on its status line while it fetches.

Command-line flight options (below) skip the start screen. Add `--menu` to open it pre-filled instead.

### Flying: command line and keys

```bash
cd game
~/.local/bin/godot --path .                                   # start screen
~/.local/bin/godot --path . -- --airport=VAJJ                 # skip it: Juhu, longest runway, engine idling
~/.local/bin/godot --path . -- --airport=VABB --runway=27     # Mumbai runway 27
~/.local/bin/godot --path . -- --airport=VAPO --air=2000      # airborne, 5 nm final to Pune at 2000 ft AGL
~/.local/bin/godot --path . -- --aircraft=a320 --airport=VABB --stand   # the A320 at a gate, cold (batteries on, engines off)
~/.local/bin/godot --path . -- --aircraft=a320 --airport=VABB --air=8000        # A320 airborne at 8,000 ft, 7 nm out, 160 KIAS, gear down, CONF 2
```

| Option (after `--`) | Meaning |
|---|---|
| `--airport=ICAO` | VAJJ (default), VABB, VAPO, VANM, VAAV (Aamby Valley), … any airport in `runways.json` |
| `--aircraft=ID` | `c172` (default) or `a320` |
| `--runway=NN` | runway end, e.g. `08`, `26`, `14`, `32`; default = the longest runway |
| `--air[=ft]` | start airborne on final at that height above the field (default: the aircraft's own, C172 1500 ft) |
| `--air-nm=N` | with `--air`: distance out on final in nm (C172 3, A320 7) |
| `--air-kt=N` | with `--air`: KIAS at the start (C172 70, A320 160; another speed sets an airliner's gear by speed: up at 200 kt or more, flaps 0) |
| `--stand[=REF]` | start parked at a stand (always cold & dark): `--airport=VABB --stand` (a jetbridge gate), `--stand="Bay 40"`, Juhu `--stand=GA3` |
| `--cold` | cold and dark: everything off, parking brake set (use the "Before Starting Engine" and "Starting Engine" checklists) |
| `--callsign=VT-ABC` | call sign painted on the tail and used on the radio |
| `--livery=…` | paint colours: see "Aircraft data: livery" |
| `--view=NAME` | initial camera: cockpit, chase (default), orbit, free, tower, wing, tail, flyby |
| `--quality=low\|medium\|high\|ultra\|max` | graphics preset (otherwise the one saved from F10) |

### Radio and ATC

**ATC** (`` ` ``) is a controller with memory, in text and optionally in the system voice. Details, phrase file and state machine: `docs/ATC.md`.
- **The radio bar** (top-left, always there in free flight) shows `COM1 118.100 · Pune Tower` (green when a unit answers, amber "no facility", red when COM1 is off or failed), the suggested next call ("Next: ask Ground for taxi") and, for 20 s, the latest controller message.
- **Calls:** click the bar or press `` ` `` to open a list of at most four plain calls with the suggested one first ("Ask Ground for taxi", "Report ready for departure", "Report final"). **↑ ↓** move, **Enter** or **1-4** call, **Esc** or `` ` `` close; it closes after a call. While it is open the arrows do not pitch and the number keys do not change the camera. Small row: **Say again** (A), **History** (H: the last 30 transmissions), **Voice** on/off (V). What you hear arrives as one card at the top centre (gone after 6-8 s).
- **Departure:** ATIS → VFR clearance (squawk, runway, readback) → pushback and taxi (the route line and follow-me car start with the call) → "contact Tower" at the holding point → ready for departure → line up and wait → cleared for takeoff with wind → "contact Approach" or "frequency change approved, squawk VFR". **Arrival:** inbound call → join / straight-in and QNH → "report final" at about 5 nm → cleared to land → "vacate runway, contact Ground" → taxi to the apron → parked.
- **Radio assist** (Options, on by default): a call tunes COM1 for you ("COM1 tuned to 118.100 Pune Tower") and the bar suggests the next call. **Off** is the realistic radio: you tune COM1, nothing is suggested, the list offers **Tune COM1 to <unit>** when needed, and a call on the wrong unit is redirected.
- Airports with no published frequency answer on any COM1 frequency (Juhu, Navi Mumbai). Small fields and heliports have no ATC: your calls are blind transmissions. A dead or switched-off COM1 sends nothing.
- **Free flight:** taking off, landing or entering a runway without clearance gives one short note per flight, never a block. **In a lesson ATC stays out of the way:** no unprompted calls, the bar is hidden (`` ` `` still opens the list), clearances count as given.
- The call sign defaults to VT-FSM when an aircraft names none (Options → Radio / ATC).

### Landing, takeoff and damage

Mistakes end the flight as in reality. Thresholds come from the C172S POH and FAR 23.

**Landing gear:**
- The wheel's oleo absorbs the touchdown: the leg strokes in and stays, rather than springing the aircraft back into the air. In the cockpit the eye dips with that stroke and settles.
- Touchdown sink rate above about 590 fpm at a main wheel is a **hard landing**: the airframe is damaged and needs inspection.
- Above about 900 fpm (about 510 fpm at the nose wheel) the **gear collapses**. Gear loads beyond the design limit also collapse it.
- **Crosswind:** touching down while drifting sideways more than about 6 kt damages the gear; more than about 10 kt folds it (ground loop).

**Strikes:**
- **Prop strike** (tip touches the ground, e.g. nose wheel first or porpoising): the engine is destroyed, and above about 25 kt the aircraft noses over (crash).
- **Wingtip strike** above 10 kt (ground loop) is a crash. A **tail strike** damages the airframe. **Ditching** (touching water) is a crash.

**What counts as a crash (obstacles):** touching any solid ends the flight, in the air or on the ground, at any speed. The card names the part and the thing ("The right wingtip hit trees at 82 kt"); the replay shows the same line.
- **The whole airframe counts:** propeller disc, nose, cowling, fuselage, both wings (edges, struts), fin, stabilizers and wheels.
- **Solids:** trees (as drawn: canopy and height), 3D OSM buildings (footprint and roof height), the landmark terminal models (real shape: you can taxi under an 8 m canopy, not into a wall), jetways, parked ground vehicles, apron floodlight masts and windsock poles. Not solid: runway and approach lights, PAPIs, signs, the follow-me car and the pushback tug.
- **No height gate:** a tall building beside a cliff is hit however far the ground is below you. Building collision data loads around the aircraft (and where it is heading), not the camera; the tile under a freshly placed aircraft is read at once.
- **Normal ground operations never crash:** stands, the pushback swing, taxiways and runways are corridors where OSM buildings and trees (not survey-grade) are forgiven, vehicles and masts that would stand in them are left out, and an overlap that exists while you sit parked is forgiven until you drive away. Terminals, jetways and vehicles stay solid.

**In-flight limits:**
- More than 2 s above **Vne 163 KIAS** damages the airframe; at **185 KIAS** the structure fails.
- **Flaps above VFE** (110 kt at 10°, 85 kt beyond) for 2 s damage and jam them.
- **Load factor** beyond +3.8 / −1.52 g overstresses the airframe; 1.5× those values breaks it (flight loads only).

**After every landing** a debrief shows sink rate, g, airspeed, pitch, bank, centreline offset and distance past the threshold, with a grade: BUTTER (under 120 fpm), SMOOTH (under 300), FIRM (under 600), HARD (under 900), DAMAGED. **After a crash** the cause and event log show; F5 restarts.

**Accuracy checks** (headless test cards):

| Check | Result | Reference |
|---|---|---|
| Takeoff ground roll | ~865 ft | POH 960 ft |
| Landing ground roll (flaps 30, full braking) | ~610 ft | POH 575 ft |
| Stall speeds, climb, cruise, glide | within 10–15 % | POH |
| Flared 300 fpm landing | no damage | — |
| 1200 fpm unflared arrival | gear collapse | — |
| Pushing onto the nose wheel | nose gear collapse / prop strike | — |
| Ditching, Vne dive, full-aft pull at 145 kt, flaps 30 at 120 kt, uncorrected 15 kt crosswind touchdown | each detected | — |

Not modelled: tyre bursts, engine damage from over-temperature or over-speed, bird strikes.

**What the instruments model:**
- **Airspeed:** C172S position error (about 6 kt low near the stall); pitot pressure falls at high angle of attack.
- **Altimeter:** Kollsman setting and slight lag. **VSI:** about 6 s to settle.
- **Attitude indicator:** vacuum-driven gyro with 3°/min erection, so it shows small turn and acceleration errors. After a vacuum failure it spins down, wanders and shows a GYRO flag.

- **Compass:** pendulous card with northerly turning and acceleration errors, swing and overshoot.
- **Turn coordinator:** electric rate gyro canted 30°, with the slip ball.

**What is modelled:**
- **Electrical:** 24 V battery (35 Ah), 60 A alternator. The alternator needs more than about 1000 RPM, so the ammeter shows discharge at idle. LOW VOLTS comes on below 24.5 V. The starter needs battery power; flaps and turn coordinator need bus power.
- **Fuel:** left and right tanks feed per the selector. The engine runs about 6 s on line fuel after starvation and restarts while windmilling when fuel returns.
- **Failures:** 26, with schedules and random ones (Start screen step 4; F9 in flight).
- **Weather** (F10 or command line):
  - **Wind:** logarithmic surface profile, blending toward the wind aloft from about 50 m (the aloft wind may be lighter). `weather/wind_table` (rows of height AGL m, from-degrees, knots), when it has rows, replaces that blend above 10 m; an empty table keeps the two-point rule. A change to the wind the pilot sets eases in over about 3 seconds. Gusts, thermals and storm cells arrive the same tick.
  - **Gusts:** along the mean wind, a new target every 3-12 s: 40 % of the time a gust of 0.3-1 x the peak (`gust_kt` - `wind_kt`), otherwise a lull of 0.2-0.67 x the peak (never below 20 % of the wind), so the mean stays the set wind (20G30 kt: mean 20, about 13-30 kt). Gusts fade out between 1000 and 1500 m AGL.
  - **Turbulence** (`world/turbulence.gd`, MIL-F-8785C as in JSBSim's Milspec model; `tests/test_weather_physics.gd`): one first-order filter per axis, u along the mean wind, v across it, w vertical, sampled exactly so 30 Hz and 120 Hz give the same statistics. Below 1000 ft AGL L_w = h and L_u = L_v = h / (0.177 + 0.000823 h)^1.2 (h in ft, at least 10 ft), and the horizontal sigma is the vertical one / (0.177 + 0.000823 h)^0.4 (about 1.7 x at 100 ft); 1000-2000 ft blends to 1750 ft on every axis with equal sigma. Time constants use the airspeed through the air mass without the turbulence. **Levels:** the Turbulence setting is a MIL-F-8785C level (menus show None / Light / Moderate / Severe: a third is light, two thirds moderate, the end severe). Below 1000 ft sigma_w = 0.1 x W20 with W20 = 45 kt x level (the standard's 15 / 30 / 45 kt); above 2000 ft the probability-of-exceedance curves of MIL-F-8785C Fig. 7 as in JSBSim (light 1e-2, moderate 1e-3, severe 1e-5: at 1750 ft about 2.1 / 2.9 / 5.4 m/s, at 3750 ft 2.3 / 3.2 / 7.0, at FL350 0.1 / 1.5 / 4.9); linear between; no growth with the wind aloft. Live weather sets the level whose low-altitude sigma is 0.1 x the surface wind (or the gust spread / 5). **Rotary gusts** (JSBSim Milspec eqs 33-35, span from `config.json` `wingspan_m`): p_g with sigma_p = 1.9 sigma_w / sqrt(L_w b), q_g = -(dw_g/dt) / V and r_g = (dv_g/dt) / V low-passed over 4b / (pi V) and 3b / (pi V); the aerodynamics see body rate - gust rate (`FDM.gust_pqr`, Props `environment/gust_pqr`, taken each tick by `fdm/fdm_air.gd`). The A320's 36 m span roughly halves its roll gusts against the Cessna's 11 m. `environment/turbulence_sigma` is the sigma_w in use.
  - **Near the ground:** all vertical wind (turbulence, thermals, ridge lift, downdrafts) fades to zero over the last 10 m above the lowest wheel (`fdm/wheel_depth_m`), smoothly through the flare, for the Cessna and the A320 on its gear alike.
  - **Pause and replay:** the weather, the storm clock, the cloud drift, the time of day and ice accretion hold while the flight is paused or a replay runs (`core/sim_hold.gd`, Props `sim/hold`). A loaded save puts the cloud field and the storm cells back where they were (`tests/test_weather_hold.gd`).
  - **Terrain effects** (`world/terrain_flow.gd`, `tests/test_terrain_flow.gd`): ridge lift on windward slopes with the full w = U . grad(h) at the surface (slope over +-500 m), decaying with height over 1.5 km (the ridge scale), -5..+6 m/s; sink on the lee side; mechanical turbulence over steep ground (decays over 400 m). **Lee waves:** every drop of the terrain upwind (sampled along the wind at 1500 m AGL every 1 km out to 40 km, five times a second, blended between updates) sends trapped waves downwind: w = -0.3 N x drop x cos(2 pi d / lambda), wavelength lambda = 2 pi U / N (stable layer N = 0.01 /s, `weather/wave_stability`; about 9 km at 15 m/s, 16 km at 25 m/s), the first lift band about half a wavelength downwind, fading over four wavelengths and above about 6 km AGL, at most +-5 m/s (about 2.4 m/s behind an 800 m escarpment). Ascents send waves of the opposite sign, so a narrow ridge mostly cancels and one about half a wavelength wide resonates. Only when the wind across the ridge (the share across the biggest drop) is above about 6 m/s, full by 12 m/s, and 60 % weaker in full daytime convection. **Rotor:** under the first crest (about 0.4 wavelength downwind of a big drop), below about 1 km AGL, a turbulence floor of up to 3 m/s. Props: `environment/ridge_lift_mps`, `lee_wave_mps`, `rotor`. Simplified: linear theory with one assumed stability, no wind-profile (Scorer) check, no rotor reverse flow, no wave clouds drawn.
  - **Atmosphere:** QNH and temperature affect density altitude and the altimeter. The Kollsman window starts at QNH.
  - **Sky:** a cumulus layer drifting with the wind aloft. Visibility drives haze: everything fades to the horizon colour with extinction 3 / visibility (5 % contrast at the visibility distance).
- **Time of day:** real sun position for Mumbai/Pune (IST). Default 10:00 on 14 February. The F10 time rate can speed it up.
- **Night:** a real moon (position and phase for the date, glitter path on water), stars, warm city glow on the horizon and cloud undersides, and a night ambient level and exposure so terrain, coastlines and clouds stay readable.
- **Cloud cover and rain** (`world/weather_visuals.gd`, `weather_fx.gd`):
  - Broken and thicker cover dims and diffuses the sun: under Overcast there are no hard shadows or sun disc, the sky and cloud base turn grey. Above the tops the sun is back.
  - **Inside cloud** (`world/cloud_look.gd`, `cloud_inside.gd`, `cloud_wisps.gd`; `tests/test_weather_visuals.gd`): the cockpit keeps a realistic short visibility (about 100 m in dense cloud); fog ramps with the camera's cloud density (in 0.6 s, out 1.2 s). Outside views cap the extinction around the aircraft so it stays visible (about 13x the camera distance, never under 3x). The inside is lighter overhead and toward the sun, darker below and in cumulonimbus and storm cores. Cloud wisps stream past as a motion cue (`wisps` in the preset table: 0 / 40 / 80 / 120 on Low / Medium / High / Ultra).
  - **Rain** falls only below the cloud tops: streaks lean with the wind and stretch with airspeed (count by preset), drops bead on the windshield when parked and run back with airspeed, wet terrain, roofs and trees get darker and glossier and dry slowly, rain rings open on wet runways, taxiways, aprons and puddles near the camera and drops splash on the ground around it, wheels throw spray on a wet surface (see "Ground particles" under Graphics), rain lowers a hand-set visibility (that number is the value between showers). A reported visibility (`weather/visibility_includes_precip`) is used as it stands. Fog denser than 800 m is not drawn. `weather/cirrus` (0 to 1, default 0.6) is the high cloud. Monsoon storms have lightning. Heavy rain lengthens a braked stop (about 1.8 times the dry distance at full rain). Rain falls where the cloud is (`WeatherVisuals.rain_rate`: the cloud-coverage field, drifting with it): a light setting (below 0.3) only as showers under the thickest clouds, heavier settings steadily, heavier under the thick parts. The rain the airframe feels (lift and drag in heavy rain, freezing rain) is the same field at the aircraft (`environment/ac_precip`); `environment/precip` is the camera's (the drawing and sounds). Under heavy rain from cumulus or cumulonimbus, rain shafts about a kilometre across push down at up to 5 m/s between the cloud base and the last ~150 m (`CloudConvection.rain_shaft`, `environment/rain_shaft_mps`). When a dew point is known, humidity raises the density altitude and does not change the temperature icing uses.
  - **Weather radar** on the navigation display (marked WX when it has a return; not on the N moving map) is the nose sweep: ±60°, a 3° beam, one colour per range cell (green, then amber, then red as the return strengthens). Dry cloud, including a dry overcast, stays black. Rain is a ragged field. A red cell leaves the rest of that radial black, the beam shadow behind heavy rain. Clear air stays blank.
  - **Live weather** (Weather step, off by default; `--live-weather`, ignored with `--lesson`): one METAR from aviationweather.gov for a station within 50 km, plus an Open-Meteo forecast for winds aloft and the fields a METAR does not carry. No METAR (Pune has none) uses the model alone. No connection uses the last fetch (`user://live_weather.json`), then the preset you had selected. The first time you turn it on, a panel on the menu (the same glass, type and buttons as the other questions) says that only a station id or coordinates rounded to about a kilometre are sent. While it is on, the presets and sliders are read-only; **Use as base** copies the numbers into the sliders and turns it off. **Update during flight** (off) fetches again every 15 minutes and eases the change in over about 5 minutes (cloud base at most 300 ft/min, QNH at most 1 hPa/min). The altimeter setting you dialled is not moved. The METAR text is added to the radio history, and ATIS includes the dew point when one was reported. The bottom attribution line gains "Weather: aviationweather.gov, Open-Meteo.com" while this is on. Lessons never fetch. Check a real reply with `tools/check_live_weather.sh`.
- **Weather physics** (clouds act on the aircraft; `world/cloud_field.gd`, `cloud_convection.gd`, `cloud_storm.gd`, `cloud_physics.gd`, run by `world/weather.gd` each physics tick; tests `tests/test_cloud_weather.gd`, `test_cloud_storms.gd`, `test_weather_physics.gd`, `test_weather_hold.gd`):
  - **Settings:** `weather/convection` (thermals 0..1: Clear 0.2, Fair 0.5, Scattered 0.7, Broken 0.6, Overcast 0.1, Winter haze 0.1, Monsoon 0.5) and `weather/storms` (microburst cells 0..1: Monsoon 0.7, else 0). Sliders "Thermals" and "Storm cells" on the Weather page and in F10. Older setups and saves load with both 0; lessons set both to 0.
  - **Cloud at the aircraft:** the CPU copy of the cloud shader's density (same noise, base `weather/cloud_base_ft`, thickness 900 m) is evaluated at the aircraft. **Towers (physics only):** cumulus reach 2500 m above the base and cumulonimbus about 11 km AMSL over the columns that are still cloud at the drawn layer's top, thinning over their last 40 % (`CloudField.density_deep`, `depth_m`): turbulence, icing, storm winds and the cockpit's in-cloud fog use them. The drawn layer stays 900 m (a deeper volumetric pass would cost every preset), so from outside a tower is invisible: you fly from clear air into fog above the drawn tops. With 30 °C at sea level the Monsoon towers cross the freezing level (about 4.6 km), so the icing setting now acts there. Type: `clear` (cover < 0.1), `stratiform` (overcast, or a high deck with little convection, or no sun), `cumulus` (daytime, convection >= 0.3), `cumulonimbus` (cover >= 0.9, rain >= 0.6 and convection >= 0.4 or storms >= 0.3: the Monsoon preset).
  - **Cloud turbulence:** the turbulence sigma is multiplied inside cloud (stratiform x1.5, cumulus x2.2, cumulonimbus x2.5), by up to half that within 300 m of a cloud, and by up to 1.4 under a cumulus base by day; and it never falls below the cloud's own floor (stratiform 0.3, cumulus 1.2, cumulonimbus 3.0 m/s; half within 300 m), whatever the setting. A storm core adds strong turbulence.
  - **Thermals:** by day (none below 2° sun elevation, full at 40°): convection x surface (water 0.15, forest 0.7-0.8, bare / urban / crops 1.0) x warmth, less under a thick deck. Updrafts of about 1-3 m/s (up to 5 under strong cumulus) in 1-3 km cells under and inside the cloud, sink everywhere between them, sized so the area-mean vertical wind below the cloud is zero (`world/thermal_balance.gd`: about -0.4 m/s between Fair-weather cumulus, about -1 to -1.3 m/s between Scattered or Broken cumulus); a long straight flight neither gains nor loses height on average. Strongest mid boundary layer, none above the cloud top or above 4000 m AGL. Added to `environment/wind_ned` like ridge lift.
  - **Storm cells (microbursts):** only in cumulonimbus conditions, about one cell per 10 x 10 km (radius 1-3 km, drifting at 0.6 x the wind aloft): downdraft up to ~10 m/s at the core, outflow shear up to ~13 m/s near the surface, an updraft core one radius to the side (up to 18 m/s in the middle of the cloud, a gentle inflow below the base, none at the 11 km top), strong turbulence, heavier rain. A cell fades out between 2.0 and 2.6 radii, so there is no wind step at its edge. Cards: "Entering cloud" / "Leaving cloud" (at most every 20 s) and "Wind shear", behind the notify option.
  - **Props at the aircraft:** `environment/ac_cloud_density` (0..1), `ac_in_cloud`, `cloud_base_m`, `cloud_top_m` (AMSL), `cloud_kind`, `turbulence_scale`, `thermal_mps` (+ up), `storm_intensity`, `storm_core`, `storm_shear_mps`, `ac_precip`, `rain_shaft_mps`, `turbulence_sigma`, `gust_pqr`, `lee_wave_mps`, `rotor`; `environment/cloud_drift`, `storm_clock_s`. `environment/in_cloud` stays the camera's (fog).
  - **Not modelled:** cloud lifecycle (clouds only drift), terrain-triggered thermals, hail, anvils, drawn towers and wave clouds (towers are physics only), the Dryden second-order v / w spectrum shape (first-order filters), roughness-dependent surface wind (z0 is one value), turbulence from buildings.
- **Runways and taxiways:** runways draw `world/runway_v2.gdshader` with the ICAO Annex 14 layout from `world/runway_markings.gd`: threshold stripes by width (18 m 4 ... 60 m 16), the designator 12 m past them (9 m block digits drawn at runtime by `runway_glyphs.gd`; L / C / R on the threshold side; the far end reads from its own approach), centreline 30 m dashes / 20 m gaps (0.9 m wide on runways 45 m or wider), edge stripes, the aiming point and touchdown-zone pairs by length (pairs within 50 m of the aiming point left out). The pavement matches the apron asphalt (or concrete slabs where `surface` says so) with paving-lane tone, patches, glossy black crack sealant, oxidised edges, a darker trafficked centre, oil drips along the centreline, worn paint, inset light fittings, and rubber: dense black tyre streaks over a broad stain in the main-gear bands from about 0.4 x to 2.5 x the aiming-point distance, heaviest just past it, heavier at the end landing into the prevailing westerlies. Every runway has its own pattern (seed from airport + ident). The static look is baked once per runway into a texture (`world/runway_bake.gd`, 0.2 m across x 0.5 m along, about 10 MB for VABB 27/09) when the camera comes within 15 km and freed beyond 20 km (`world/runway_bakes.gd`); until then a cheaper unbaked look shows and the bake fades in over 1 s. Near the camera the fine detail stays procedural (within ~220 m on High, ~300 m on Ultra / Max): aggregate texture and normal, exact sealant lines, tyre-tread streaks. **Runway detail** follows the preset (`world/runway_quality.gd`, global shader parameter `runway_detail`): Low 0 (baked look and paint), Medium 1 (+ near sealant lines and streaks), High 2 (+ aggregate texture, light fittings), Ultra / Max 3 (+ near block cracks, streaks looked up in two lanes instead of one). Taxiways (`world/strip.gdshaderinc`) share the pavement include: lighter wear, the yellow 0.15 m centreline, double yellow edge lines where OSM gave a width (`width_known`). Review shots: `tests/debug_runway_preview.tscn` (`RWPV_*` options in its header), cost per megapixel: `tests/debug_runway_bench.tscn`. Tests: `tests/test_runway_markings.gd`, `tests/test_runway_shader.gd`.
- **Aerodrome lighting (night):** built per airport within 25 km: runway edge lights (last 600 m yellow on instrument runways), threshold / end bars, centreline lights and touchdown-zone barrettes on ILS runways, ALSF-II-style approach lights with sequenced flashers on ILS ends (a 420 m simple system elsewhere), a PAPI left of each runway (2 red + 2 white on a 3° path, visible by day), blue taxiway edge and green centreline lights, red stop bars and runway guard lights at holding points (night, visibility under 5 km), rotating beacons. Lights are directional, fade in haze and dim by day.
- **Apron floodlights** (`world/apron_light_layout.gd` places, `apron_floodlights.gd` draws, `light_pool.gdshader` lights the ground of the far banks from the depth texture and skips the sky and daylight (Forward+ only reads depth; the NaN it produced on sky pixels was the day flicker of docs/FLICKER-PLAN.md), `apron_lamps.gd`, `stand_boards.gd`, `apron_mask.gd`): every stand of a lit airport gets light: 15-28 m masts between airliner stands (about one per two stands), 10 m poles on GA aprons, floods on the terminal facade above contact stands with a lit stand-number board. A mast never stands in a corridor, in a stand's parking box or within 7 m of a jetway, and is no taller than (distance from the runway edge − 30 m) / 4; masts and poles are solid. Lamp colour per airport: `airport_ops.json` `apron_lamps` ("led" ~4000 K / "hps" sodium) or a hash of the ICAO code. On from just before sunset. Near the camera the banks are real SpotLights (preset `real_lights`: 2 Low, 4 Medium, 10 High, 16 Ultra, 24 Max, at most 4 on Mobile; `apron_shadows`: the 1 (Ultra) or 2 (Max) nearest banks cast shadows); elsewhere a light volume (`light_pool.gdshader`) adds the same light from the depth buffer, cross-faded by distance. Not modelled: docking guidance boards.
- **Aircraft lights** (night): red / green nav lights (110° forward sectors), white tail light (140° aft), red beacons (C172 fin top; A320 crown and belly), white double-flash strobes (wingtips; A320 tail cone too), drawn as glowing points with a minimum on-screen size so the aircraft is visible from miles away. Landing and taxi lights are spot lights with a faint beam and a lit pool ahead (fading out above ~80 m AGL). The A320 adds retractable landing lights (lit once extended), taxi + take-off and two runway turn-off lights on the nose gear, logo lights and wing / engine scan lights. Every light sits on its housing in the model (`tests/test_aircraft_light_placement.gd`; `tools/glb_probe.py` measures a model; scenes `lights_a320_front`, `lights_c172_tip`, ... in `tests/showcase_light_scenes.gd`).
  - **Lights at start** (night or dusk, sun below 5°): nav + beacon always; strobes for air and runway starts; landing light for runway starts and air starts below 3000 ft AGL; taxi light for runway starts (the A320 also gets take-off, runway turn-off and logo lights). Cold & dark and stand starts: everything off. By day: beacon only.
- **Cockpit at night:** instruments are internally lit and follow the PANEL dimmer (default 70 %; unpowered = dark), radio displays stay lit, a warm glareshield flood lights panel and yokes.

**Realism notes:**
- With only the pilot aboard (default load) the CG sits slightly left and engine torque also rolls the aircraft left. Fixed aileron / rudder tabs (`controls.aileron_rigging` 0.033, `rudder_rigging` 0.004) cancel this at about 100 KIAS in level flight. Slower or at climb power it rolls gently left; faster, slightly right. Hands off from trim the bank after 60 s is about −10° at 90 KIAS, 0° at 100, +10° at 110. JSBSim's c172p does the same (nearly neutral spiral mode): `docs/FDM-VS-FLIGHTGEAR.md`.
- The aircraft turns left on the takeoff roll (P-factor and torque): use right rudder (X).
- **Sound** uses real recordings: the C172 engine (start, crank, idle, run, cut, pitched by RPM), stall horn, gyro spin-up, flap motor, trim wheel, tyre roll, touchdown squeal (one 3D player per gear leg: `world/tyre_squeal.gd`), wind by airspeed, switch clicks and levers (cockpit only). Sources and licences: `game/aircraft/c172/sounds/SOURCES.md`.

### Icing and rain

Ice forms in cloud with static air temperature between about +2 and −20 C. In the tropics that is high: with a 30 C day the freezing level is near FL150 and the band runs to about FL250, so the A320 can ice in cloud at FL150-FL250 and the C172 hardly ever does. **Icing** (0-100 %, Weather page and F10; `--icing=0..1`) sets how much supercooled water the cloud holds. Presets: Clear / Fair 0, Scattered 0.2, Broken 0.4, Overcast 0.5, Winter haze 0.2, Monsoon 0.7; storm cells add their own share; older saves have 0.

- **Accretion** (`systems/icing.gd`, numbers in `icing_rates.gd`): rate = cloud density x airspeed x liquid water (stratiform 0.4, cumulus 1, storm 1.5) x availability x temperature factor (peak −3 to −15 C). Dense cumulus at availability 1 fills the airframe in about 5 min, freezing rain (rain below 0 C) in about 2 min. Out of conditions ice sublimates in about 30 min and melts within minutes above +5 C.
- **Effects at full airframe ice** (`fdm/environment_effects.gd`): drag `drag_k` (C172: +35 % CD0, +22 % total drag at 100 KIAS), lift near the stall x(1 − `clmax_k`) with stall alpha down 11 % (CLmax −27 %; stall speed +12 % in the flight test: 53.8 → 60.2 KCAS), lift slope −3 %, earlier stall warning. Inlet ice scales piston power or turbine thrust by `1 − power_loss_k x ice` (C172 −25 %, A320 −20 %; turbine EGT rises by `egt_k`). Heavy rain (`environment/precip` above 0.6) costs up to 3 % lift and +0.0012 CD (1 % N1 on a turbine).
- **Pitot and static ice:** a probe above 0.7 ice (static 0.9) behaves like `failures/pitot_blocked` / `static_blocked` until it falls below 0.4 (0.6). The alternate static source bypasses an iced static port.
- **Protection** (`aircraft.json` `icing`, all keys optional, defaults in `Icing.DEFAULTS`): `protection` is `none`, `pitot_only` (C172: PITOT HT with bus power; optional `controls/alt_air` lever clears induction ice) or `wing_and_engine` (A320: wing and engine anti-ice from running engines' bleed air, costing thrust: `bleed_wing` 1.5 % and `bleed_engine` 2 % per engine; probes heat automatically). Other keys: `drag_k`, `clmax_k`, `power_loss_k`, `egt_k`, `pitot_heat_prop`, `wing_anti_ice_prop`, `engine_anti_ice_prop` (`%d` = engine number), `bleed_*`, `rain_cl_k`, `rain_cd_k`, `rain_n1_k`.
- **Airliner switches:** the overhead ELEC, HYD, FUEL, AIR and SIGNS switches are clicked in the cockpit or bound on the Controls page (no default keys). Ctrl+W wing anti-ice, Alt+E / Alt+D engine 1 / 2 (rebindable; `controls/anti_ice/{wing, eng_1, eng_2}`; probe heat `controls/anti_ice/probe` is on from the start). The E/WD memo shows ICE DETECTED (amber until anti-ice is on) and ANTI ICE. The C172 has only PITOT HT.
- **Props:** `icing/{airframe, pitot, static, engine_<n>}` (0..1), `icing/{rate, conditions, ice_detected, pitot_blocked, static_blocked, bleed_penalty, bleed_penalty_<n>}`. Read: `environment/ac_cloud_density` (in cloud above 0.05), `cloud_kind`, `storm_intensity`, `precip`, `weather/icing`, `atmosphere/temperature_k`. The state is saved with a flight (`icing`). Cards: "Ice accretion - leave icing conditions", "Pitot icing - airspeed unreliable", "Engine icing".
- **Not modelled:** ice weight, ice on the tail (the elevator is not degraded), A320 FBW protections moving with ice, de-icing boots, runway and ground ice, structural or engine ice damage, wiper / windshield heat, humid-air carburettor ice. Rates and effects are plausible, not tuned to an aircraft's data.

### Post effects

Code: `core/post_fx.gd` (`PostFx.apply(root, preset)`, after the graphics preset), rules in `core/post_fx_rules.gd`, looks in `core/post_fx_look.gd` (pure, `tests/test_post_fx.gd`), effects in `world/postfx/`. | `motion_blur` (on) | High | Forward+ | per-pixel blur along the velocity buffer, camera reprojection for the sky; scenery beyond the aircraft never moves faster than the camera's own turn and travel explain (cap per pixel); 180° shutter normalised to 60 fps; reset on floating-origin shifts and view switches |
| `sun_shafts` (on) | Medium | Forward+ | screen-space rays from the sun, occluded by terrain, cockpit and cloud |

| `color_grading` (on) | Low | both | contrast / saturation / white balance by sun height, cloud and rain; brightness untouched |
| `heat_shimmer` (on) | High | Forward+ | over sunny ground when low, and behind running exhausts (`exhausts` in aircraft.json) |
| `lens_rain` (on) | Medium | both | drops on the lens in outside views only |
| `lens_effects` (off) | Low | both | vignette, chromatic aberration, film grain |
| `depth_of_field` (off) | Low | both | focus on the aircraft; replay and free camera only |
| `volumetric_fog` (on) | High | Forward+ | near-field froxel fog (below) |

**Volumetric fog** (`world/volumetric_fog.gd`, `vfog_rules.gd` (pure maps, `tests/test_volumetric_fog.gd`), `vfog_composite.gd/.gdshader`, `vfog_air.gdshader`, `vfog_rain.gdshader`): Godot's Environment volumetric fog with FogVolumes, driven from the weather props every frame. It gives light shafts under broken cloud, rain curtains under storm cells, streaks in heavy rain, puffs in cloud and glow round real lights at night. Preset key `vfog` = froxel quality: 0 Low / Medium (off, Mobile), 1 High (64² × 64 froxels, 5 km), 2 Ultra (96² × 96, 10 km), 3 Max (128² × 128, 14 km), with temporal reprojection. Morning mist is built but off (`VfogRules.MIST_ENABLED`; it still shows a hard edge a few km out, see `docs/GRAPHICS-PLAN.md` G5).
- Godot accumulates FogVolume density in fixed point (about 1/1024 per m; smaller values vanish), so thin air is the Environment's `volumetric_fog_density` and the FogVolumes only carry dense things or cut the thin air away (one box round the camera in cloud shadows and above the haze top; up to 4 cylinders under the nearest storm cells).
- Materials with `render_mode fog_disabled` (terrain, buildings, trees, runways, vehicles, cloud pass, rain, light points) skip Godot's volumetric fog. `VfogComposite` (child of the camera, first of the transparents) puts it back with n + 1 full-screen planes at fixed depths; the albedo is pre-inverted, so it needs plain exponential Environment fog (`VfogComposite.env_fog_invertible`, otherwise the fog switches off with a warning). Pixels nearer than the aircraft keep the engine's own fog.
- `--no-vfog` (user arg) turns the effect off for before / after renders.
- Godot 4.7 quirks: global shader uniforms read wrong values in `shader_type fog` shaders (pass cloud-shadow inputs as material parameters); a `Color` given to a `vec3` uniform arrives linearised again (pass a `Vector3`).

### Adding an aircraft

An aircraft is a folder `game/aircraft/<id>/`; nothing else in the game names an aircraft. Everything is read through `AircraftDef` (`game/aircraft/aircraft_def.gd`: `load_def(id)`, `current()`, `path(key)`, `config()`, `section(name)`, `section_or(name, defaults)`; an unknown id falls back to the c172). Generic code (cockpit, lights, audio, glass, reflections) is in `game/aircraft/common/`, the model loader is `game/aircraft/aircraft_model.gd`.

```
game/aircraft/<id>/
  aircraft.json    what the game shows and needs: name, specs, limits, systems, ... (sections below)
  config.json      flight model: mass, gear, tanks, engines, controls
  aero.json        aerodynamic tables (JSBSim form, tools/06_jsbsim_to_json.py)
  hull.json        collision outline (optional)   checklists.json   panel.json   (optional)
  models/exterior.glb, models/interior.glb, sounds/   (optional; a placeholder airframe is drawn without a glb)
```

Any file name can be overridden with a `files` map in `aircraft.json` (`{"config": "other.json"}`). The A320 folder can also be shipped on its own: `tools/package/make_pack.sh` (see "A320 data" and "Building and installing release packages"). The C172 stays in the base game either way.

`aircraft.json` sections: `model`, `cockpit`, `lights`, `audio` ("Aircraft data: model, cockpit, lights, audio"), `limits`, `damage`, `systems`, `payload`, `start`, `failures` ("Aircraft data: limits, systems, payload"), `ground`, `pushback`, `ramp`, `exhausts`, `registration`, `icing`, `fcs`, `replay`, `livery`, `cameras`, `atc`, `radio_type`, and `controls.flaps_lever` (Captain Pack, below). Defaults are the C172's.

**`ground`** (structural-frame metres about the CG; code `world/ground_params.gd`):
- Footprint that stands, taxi corridors and jetways are sized for: `ahead_m` (3.3, forward incl. margin), `behind_m` (7.4, to the tail), `across_m` (6.7, half span), `height_m` (2.5, what a jetway or tunnel must clear).
- `tow_ahead_m`: tug position ahead of the CG during pushback. `tug_scale` (1): size of the tug model; `tow_ahead_m` is its origin, so for a scaled tug add its cradle (about 2.9 m x scale) to the nose gear position.
- `min_runway_m` (0): the start screen marks shorter runways "too short for this aircraft"; they are never the default pick and rank last for the wind-based runway choice of taxi guidance and ATC. C172 175.3 (575 ft, POH landing roll at sea level, no margin), A320 1800.
- `cg_to_door_m` (0): L1 door ahead of the CG. At a jetbridge gate (whose stand point is the door's place on the centre line) the CG is placed that far behind it. `door_y_m` (0): lateral offset of the L1 door from the centre line, negative = left (the jetway hood face docks at this offset minus 0.15 m outside the skin, its centre `door_w_m` / 2 + 0.05 m ahead of the doorway so the open door swings inside the canopy: `GroundParams.hood_fwd_m`).
- `door_height_m` (absent = `height_m`): what a jetway part must clear before it counts as solid in a corridor. **Its presence also makes the jetways of a gate dock to this aircraft** (cab floor to this sill height); the C172 has none, so its jetways stay at rest (straight toward the cab end, the hood 5 m short of it).
- `doors` (absent = the one L1 door from the keys above): every door that opens, `[{id, label, kind: passenger | cargo, x_m, side, sill_z_m, w_m, h_m}]` in structural metres (`world/cabin_door.gd`; L1 keeps `controls/door_open` / `systems/door_pos`, the others `controls/doors/<id>` / `systems/doors/<id>`; key actions `door_toggle`, `door_r1_toggle` ..., `passenger_doors_all`, `cargo_doors_all`, offered through the `doors` action group). Panels lie on the skin measured by `aircraft/common/skin_probe.gd`.
- A320 passenger doors are modelled: `models/doors.glb`, made by `Blender -b --factory-startup --python tools/blender/a320_door.py` (with `a320_door_geom.py`, `a320_door_parts.py`), built on the `exterior.glb` skin from `ground.doors`; aircraft.json `files.door_model` names it. `CabinDoorPanel` uses it for passenger doors (without it, or for a door missing from the glb, the grid panel); cargo doors stay plain panels. Nodes per door `<id>`: `_leaf` (rides `CabinDoorPanel.offset`), `_handle` (lifts 165° over the off-the-stops travel: down = closed and locked, up = unlocked), `_lock_locked` / `_lock_unlocked` (green / red indicator), `_arm` (pivot pin in the forward frame, turns by the swing angle; `_arm_end` stays on the door fitting), `_frame` (lining, sill, stops, assist handles, lit galley) and `_mask`. The skin has no hole, so the doorway is drawn through a stencil portal (`CabinDoorModel`, `door_portal_depth.gdshader`): the mask writes stencil 90, a reset pass sets far depth there, and the doorway plus a stencil copy of the door and arm draw inside with normal depth. Slide arming is always shown DISARMED (lever up, pin and streamer); the cabin-pressure and slide-armed lights are unlit. Test: `tests/test_doors.gd`.
- `nose_gear_m` (0): nose wheel ahead of the CG, where the stand stop bar is drawn. `taxi_half_m` (8): half width of the taxiway corridor where OSM obstacles are forgiven.
- `max_taxi_kt` (absent = no advice): shows "Taxi speed N kt, keep it under M kt" while a taxi route is active. `follow_gap_m` (absent = max(35, `ahead_m` + 25)): the follow-me car leads by that much, starts 5 m further ahead and peels off 10 m before it. `hold_short_m` (40): distance of the "Hold short" call.
- `stand_class`: `"any"` (no preference: first jetbridge gate is the default stand; taxi-to-apron prefers ramp stands), `"gate"` (jetbridge gates and remote bays, no GA tie-downs, gates first; taxi-to-apron prefers gates), `"ga"` (tie-downs first). A stand is a gate if `jetbridge`, GA if its ref starts with GA or it is synthesised, else remote (`world/ground_choice.gd`).
- Top-level `pushback`: `{"straight_m": 30, "radius_m": 18, "speed_mps": 1.4}` (preferred straight back and turn radius). The tug aims the tail at the taxiway behind the stand and shortens the arc so the wheels stay inside the paved edge (`world/pushback_fit.gd`); stand corridors follow that arc. Jetway docking: a 6 s extend / retract when the aircraft parks at or leaves the gate (`world/jetway_docks.gd`, `docs/A320-STATUS.md`). Once the bridge stops, the cab's canopy (bellows over the sides and top, floor plate with a rubber bumper: `world/jetway_canopy.gd`, `jetway_canopy_mesh.gd`) is lowered over 2 s; its front edge is ray-cast onto the aircraft's exterior meshes, so it touches the real skin all round (nose taper, crown, any cab angle). Then the door is asked open. Leaving: door shut, canopy folded, bridge back.
- Not done: a taxiway width filter in the route search; a stand size class in `tools/airport_stands.py`.

**Other top-level keys:**
- `radio_type` (how the pilot calls the aircraft, e.g. "Cessna 172", the `{type}` slot in `atc/phraseology.json`). `atc` `{profile: "ga" | "airline", wake: L|M|H|J}`; an airliner adds `telephony` (fictional airline name), `flight_no`, `callsign_style: "airline"` (radio call sign "Skyline 123"; IFR phrases, no VFR circuit: "Airline profile" in `docs/ATC.md`).
- `cameras`: `chase` `[back_m, up_m, follow_per_s]` (third value optional, default 4). The camera sits `back_m` behind and `up_m` above the CG, plus a trail of ground-speed / `follow_per_s` that eases over about a second, so a speed change or a long frame does not zoom the view; the heading eases at `follow_per_s`. `wing` `[x, y, z, yaw_deg, pitch_deg]` (pair optional, default 20° left / 8.6° down), `tail` `[x, y, z]`, `orbit_m`; render frame about the CG (x right, y up, z aft). Default: the C172's scaled by wingspan. `flyby` (optional, `ui/flyby_placement.gd` DEFAULTS): the fly-by camera (8) stands `lead_s` (5) s of ground speed ahead, clamped to `ahead_sizes` [3, 40] aircraft sizes, `side_sizes` (2.3) off the track and `up_sizes` (0.45) above the pass point; size = max(wingspan, `ground` ahead_m + behind_m). Zoom keeps the size at `frame` (0.42) of the frame height between `fov_min` / `fov_max` (10 / 55°). It lifts 3 m (+5 % of size) above terrain and obstacles, picks the best of 18 candidates (skipping hidden or in-cloud ones) and re-places at `replace_k` (0.9) x the placement distance past it; a jump over 25 m counts as a camera cut for the post effects (`tests/test_flyby_placement.gd`).
- `start`: `pitch_trim` of a parked start; `start.air` (see "limits, systems, payload"). In `limits`: `vr_kias` (Rotate call), `vs0_kias` (Airspeed-alive call).
- `registration` paints the tail number on the exterior texture at flight start (`aircraft/common/registration_paint.gd`): `source` `"callsign"` (the pilot's call sign; `text` is the aircraft's own registration shown until one is typed: C172 VT-LBR, A320 VT-ZZA) or `"fixed"` (+ `text`: pilot cannot change it); `texture` (atlas, relative to the aircraft folder); `targets` `[{erase [x,y,w,h] (pixels of the old number plus a margin), text [x,y,w,h] (box the new one is fitted into, aspect kept), align left|right|center, color [r,g,b], italic}]`. A target also takes `rotate: 90 | 180 | 270` (turned atlas island), `erase_axis: "x"` (wipe a vertical number between the clean columns beside it) and its own `texture` (the C172 repaints the number on both wing undersides too). No section = the model keeps its own number. `baked` = the atlas already carries this number, paint nothing (only the C172: 4X-CHV). Check a target by eye: `godot --path game --windowed --audio-driver Dummy res://tests/debug_registration.tscn -- --aircraft=c172 --out=<dir> --texts=VT-LBR,N172SP`.

**`ramp`** (optional): where the ramp crew services the parked aircraft and what it must keep clear (`world/ramp_points.gd`, `ramp_layout.gd`, `ramp_crew.gd`). Frame `[forward, right]` metres about the CG on the stand, heights in metres above ground. Keys: `fuselage_half_m`; `wing` and `tailplane` `{outline: [[f, r], ...] (right side, mirrored), low_m: [root, tip] (underside height; a vehicle 0.4 m lower may stand under it)}`; `engines` `[{at: [f, r], length_m, radius_m, intake_m, exhaust_m}]` (each engine listed, no mirroring; danger zones ahead and behind are kept clear); `gpu` (ground-power receptacle), `refuel` (coupling or filler cap), `cargo` `[[f, r], ...]` (a baggage tractor and two carts each), `doors` `[[f, r], ...]` (the first gets the apron bus at a remote stand), `tug` (false = no tug ahead of the nose). `gpu` / `refuel` may be `null`.
- Every missing key is derived from the aircraft's size (config.json, engines, gear, `ground` footprint): a straight wing at the aero reference point; aircraft longer than 20 m also get a GPU near the nose, a coupling under the right wing, forward and aft holds on the right and the L1 door; smaller ones none.
- Layout: tug ahead of the nose wheel, GPU beside the receptacle, a hydrant dispenser (jetbridge gate, airliner) or fuel truck at the coupling, baggage trains at the cargo doors, the bus at a remote stand. Each slides away from its point until it is 0.8 m clear of the airframe keep-out, other crew vehicles and every registered solid; one with no room within 14 m along / 4 m out is left out.
- The crew comes when the aircraft stands on a stand point (CG within 3 m, heading within 20°) with the parking brake set and engines stopped (a stand start: at once) and leaves when the brake is released, an engine starts or the aircraft leaves. While there it is solid (`ObstacleRegistry` group `ramp:<ICAO>`) but allowed in its own stand's corridor. Prop `ops/ramp_crew` names the stand and vehicle count. Fixed-offset vehicles at other stands (`AirportOps.SERVICE`) stay. Not modelled: belt loaders, catering trucks, cones.
- C172: receptacle on the left forward fuselage, left-wing filler cap, no holds or doors, `tug: false`. A320: GPU at the nose (right), coupling under the right wing outboard of the engine, holds on the right, L1 / L4 on the left, CFM56 nacelles with 3 m intake and 6 m exhaust zones. Test: `tests/test_ramp_service.gd`.

**`exhausts`** (optional) gives the heat shimmer behind running engines (`world/postfx/heat_shimmer.gd`): `{"strength": 1.0, "list": [{"pos": [x, y, z], "dir": [x, y, z], "radius": m, "kind": "jet" | "piston", "engine": n}]}`. `pos` / `dir` are in the model frame of `models/*_pivots.json` (FlightGear: x aft, y right, z up, metres from the VRP; `dir` defaults to straight aft); `engine` is 1-based and the plume is as hot as that engine's `engines/<n>/running` and `egt_k`. Optional per entry: `length_m` (default 30 x radius for a jet, 25 x for a piston stub), `spread` (end radius / nozzle radius: 2.5 jet, 4 piston), `strength` (1 jet, 0.35 piston). Up to 4 plumes; no section = no shimmer. Each plume disc distorts a pixel by the share of its gas in front of that pixel's surface (the ray's chord through the disc), and the plume grows in over its first sixth: the nacelle and the engine at the nozzle stay sharp. A flat 0.5 m depth tolerance used to ripple the rear of the engine itself. Other post effects need no aircraft data.

**`config.json` engines.** The older single-engine form `{"engine": {...}, "propeller": {...}}` is one piston engine. For any number of engines use a list (each engine carries its own `propeller` block):

```json
"engines": [
  {"type": "piston", "pos_m": [-0.96, -1.6, 0.68], "maxhp": 180, "...": "as the c172 engine block", "propeller": {"diameter_m": 1.9, "...": "..."}},
  {"type": "turbine", "pos_m": [1.0, 1.6, 0.9], "thrust_n": 12000, "max_rpm": 100, "idle_n1": 0.22,
   "spool_up_s": 5, "spool_down_s": 3, "tsfc_kg_per_n_s": 1.6e-5, "alt_exponent": 0.8, "mach_lapse": 0.3, "windmill_drag_n": 36, "start_n1": 0.25}
]
```

`pos_m` is the thrust point in structural metres (x aft, y right, z up). `type` is `piston` (engine plus propeller, `fdm/engine_piston.gd`) or `turbine` (no propeller; `fdm/engine_turbine.gd`: N1 spool, thrust from N1 with density and Mach lapse, fuel flow = `tsfc * thrust`, windmilling drag when failed or out of fuel). Optional `cruise_rpm` / `start_rpm` set the thruster speed of an airborne / ground start. Engine 1 uses `controls/throttle`, `mixture`, `starter`; engines 2..N use `controls/throttle_2` ... (falling back to the engine-1 lever) and `failures/engine_2` ... `tanks` is any list (`pos_m`, `capacity_kg`, `contents_kg`); a tank's side (left / right / centre) comes from its y position; the fuel system (`systems.fuel.feed`: `selector` or `all`) decides which tanks feed.

`gear` entries take an optional `role`: wheels `nose`, `main`, `tail`; structure points `wingtip`, `tail_skid`, `skid`. If missing it is derived: a steered wheel ahead of the fixed wheels is `nose`, behind them `tail` (a taildragger, using the nose wheel's weaker-leg limits), structure points by name (`TIP`, `TAIL`). `brake_group` is `LEFT`, `RIGHT`, `BOTH` or `NONE`.

**Generating the flight model.** `config.json` and `aero.json` of a JSBSim-based aircraft come from `tools/06_jsbsim_to_json.py [id]`: add an entry to `SPECS` (JSBSim aircraft, engine and propeller file names, rigging, gear damping, V-speeds, ...) and run `$PY tools/06_jsbsim_to_json.py <id>` (default `c172`; the committed c172 files regenerate byte for byte). Other aircraft write the two JSON files by hand. `tests/test_generic_aircraft.gd` builds a twin piston, a taildragger and a twin turbine from the c172 data in code (`AircraftDef.make`): a good template for checking a new configuration.

### Tuning the aircraft

Behaviour is data, so tune without touching code:
- `game/aircraft/c172/config.json`: mass, inertia, gear springs and friction, surface limits, flap timing, engine and prop. `propeller.ct_factor_vs_j` (thrust multiplier versus advance ratio) and `cp_factor` are the main performance knobs.
- `game/aircraft/c172/aero.json`: aerodynamic coefficient tables and constants, from JSBSim.
- Both files are regenerated by `tools/06_jsbsim_to_json.py`: put permanent changes in that script (or stop regenerating).
- `controls.full_travel_s`: actuator rate limits (seconds for full −1..1 travel; pitch 0.3, roll and yaw 0.15, from FlightGear's c172p).
- Re-run the test cards and `tools/18_compare_fdm.py` after any change.

### Aircraft data: limits, systems, payload

Numbers that belong to one aircraft are in its `aircraft.json` (via `AircraftDef`); scripts hold only defaults.

- `limits`: `vne_kias`, `vd_kias`, `vfe_kias` (`[[max flap deg, KIAS], ...]`), `g_pos`, `g_neg` (damage model), `vs0_kias`, `vs1_kias`, `vno_kias`, `asi_min_kias`, `asi_max_kias` (ASI arcs and scale; the white arc ends at the last `vfe_kias` speed), `max_crosswind_kt` (C172 15, A320 33; missing = 15; used by the "Fly anyway" check and the wind dial), `tach` (`max_rpm`, `green` `[lo, hi]`, `red`) and `gauges` (`fuel_gal`, `oil_temp_f`, `oil_press_psi`, `egt_f`, `fuel_flow_gph`, `suction_inhg`, `ammeter_a`, each `{min, max, green: [lo, hi], red}`; `red` optional; a gauge left out is not shown on the engine strip).
- `damage`: `hard_landing_ms`, `collapse_ms`, `nose_collapse_ms`, `collapse_drop_m`, `side_damage_ms`, `side_collapse_ms`, `main_load_w`, `nose_load_w`, and `prop_hubs_m` (one `[x, y, z]` structural position per engine, for the prop-strike check).
- `systems.electrical`: `battery_ah`, `alt_max_a`, `alt_rpm_min`, `alt_rpm_ramp`, `bus_volts`, `bat_v_empty`, `bat_v_full`, `bat_ohm`, `charge_gain`, `charge_min_a`, `starter_a`, `flap_motor_a`, `low_volts`, `powered_volts`, `starter_min_volts`, `loads` (amps per consumer). Defaults: `systems/electrical.gd`.
- `systems.pitot_static`: `pos_err_kcas` and `pos_err_dkt` (airspeed position error table, kt; none = no error). `systems.fuel`: see `systems/fuel.gd`.

  Where the numbers come from (a landing start, level a little under the 3° path, about 1.5 minutes before the stabilisation point at 1,000 ft IMC / 500 ft VMC):
  - 3° path = 318 ft per nm (FAA AIM 1-1-9 https://www.faa.gov/air_traffic/publications/atpubs/aim_html/chap1_section_1.html; FAA JO 7110.65 5-9-1 https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap5_section_9.html: join the glide slope at or below it). Stabilisation heights and criteria: FSF ALAR 7-1 via https://skybrary.aero/articles/stabilised-approach.
  - A320: Airbus briefing note "Aircraft Energy Management during Approach" https://skybrary.aero/sites/default/files/bookshelf/166.pdf (10 to 20 kt per nm of deceleration on the path with landing flaps and gear; stabilised at 3 nm / 1,000 ft; CONF 2 before the final descent point when the intercept is below 2,000 ft AGL, Airbus Safety First #24 https://skybrary.aero/sites/default/files/bookshelf/4071.pdf). Vapp about 135 to 140 kt at 62 to 64 t (second-hand: https://www.scribd.com/document/332863022/a320-Landing-Performance). Measured in the sim: 139 kt, CONF FULL, on the path at 1,000 ft (3.15 nm) 103 s after the start, near-idle thrust.
  - C172: the Cessna 172S Information Manual (https://umaine.edu/flyingclub/wp-content/uploads/sites/382/2016/10/CessnaAIM_172SNAVIII_SkyhawkSP172SIMAUS.pdf) gives 60 to 70 KIAS flaps full on a normal approach, 61 short field; 3 nm out is about 950 ft. Flaps 20° at 70 KIAS oscillates in this model, flaps 30° at 70 KIAS is calm.
  - A missing key is derived by `aircraft/air_start.gd` (`AircraftDef.air_start()`): `kias` from the older `start.air_kt`, else 1.3 x `limits.vs1_kias` rounded to 5 kt (no vs1: 90); `dist_nm` from that speed (under 120 kt 5 nm, up to 160 kt 8, above 11); `alt_ft` = `dist_nm` x 318 rounded to 100 ft; gear down, flaps 0, limits 300..12,000 ft / 1..25 nm. A new aircraft needs no block. With another speed (`--air-kt`, a lesson) the gear follows the speed and flaps are 0.

An old `last_flight.json` without the flag counts as custom unless it holds exactly 1500 / 5 / 90; without `air_kt_given` its speed is kept only if it is not any installed aircraft's own air-start speed and lies in the safe range.

### Thrustmaster TCA Captain Pack X (Airbus): sidestick and quadrant

Controls page > Joystick & gamepad > **Reset: Airbus Captain Pack** (`core/input_profiles.gd`, `InputProfiles.captain_pack(os)`) loads the profile for the Thrustmaster TCA Captain Pack X, Airbus Edition. **Set the switch on the back of the sidestick to PC** (in Xbox mode macOS and Linux see no joystick at all). **Plug the quadrant into the computer or hub directly**, not into the sidestick's USB-A ports: it then shows up as its own pad, `TCA Q-Eng 1&2`. Pads are found by name ("sidestick", "q-eng"; a binding's `name`), then by guid, then by index, so the two USB devices resolve in any plug-in order. An action only acts on an aircraft that offers it, so one physical control can mean something else per aircraft.
- Sidestick: roll, pitch, twist = rudder, trigger = brakes (hold), hat = pitch trim, red button = cockpit camera, right base keys X = map, Y = flaps up, A = flaps down, B = parking brake toggle. The three buttons on the front of the base: change view (button 19) = next camera, menu (three lines, button 21) = pause, Xbox (button 20) = unbound. To use another button for the next camera, press Bind on the "Next camera (C)" row of the Joystick tab and press the button. The base wheel is unbound; bind it to Nosewheel tiller on the Joystick tab. The left base keys and the grip's other buttons are unbound.
- **Invert a switch:** a latching switch (gear lever, engine masters, parking brake, magneto switch) has an **Invert** toggle on its row in Controls > Joystick & gamepad. It swaps on and off for that binding (`invert` in the binding). Axes have their own Invert under Tune. Clearing a binding clears its invert.
- **Numbers are measured** (owner's hardware, macOS 27.2, Godot 4.7.2 = SDL3, capture 2026-11-04, `tools/hid_probe.swift` raw HID capture and `tests/probe_pads.gd`; Godot's values equal the raw normalised HID values, and Godot numbers axes by ascending HID usage, so the quadrant's descriptor order 0,1,2,3 is Godot axes 0,1,2,5). **Linux numbering has not been checked**: press Bind on any row to capture the real one and record lasting differences in `OS_OVERRIDES` (`core/input_profiles.gd`).
- **Move each lever once** after starting: on macOS a lever reports nothing until it has moved, and until then libresim ignores it (the keyboard still works). Latching switches and selectors are read from the hardware when the flight starts, when F5 restarts it and when a pad is plugged in (see the table); the flaps lever acts only when moved.
- **Lo / Hi** (axis rows, inside Tune): put a lever at its idle end and press Lo, at full and press Hi (a `*` shows it is set). Raw values beyond an end clamp (`lo` may be above `hi`: the quadrant levers read falling when pushed forward). A new Bind or clear drops `lo`, `hi`, `rev`, `clicks`, `detents` and `values` (`InputBindings.CAL_KEYS`).
- Binding data (all in the profile, per lever): thrust levers carry `lo` (raw at idle, lever 1 +0.465 = the middle of its resting range +0.445 .. +0.488, lever 2 +0.47), `hi` (raw at TOGA, -1.0), `rev` (raw at full reverse, +1.0) and `clicks` (`{raw, detent, play}`: the physical clicks and the sim detent each one is). `LeverDetents.forward_pos` maps the raw value piecewise through idle -> 0, the click -> that detent's position over +-`play` of raw, TOGA -> 1, so the CLB and FLX/MCT clicks land exactly on the A320's CL (0.556) and FLX/MCT (0.778) detents; clicks whose detent the aircraft does not have are skipped (the C172 is linear idle..TOGA). Behind idle (`LeverDetents.IDLE_BAND` = 0.05 of raw travel of idle play) it is reverse, growing linearly to REV MAX at `rev`. The speed brake lever carries `detents` + `values` (nearest stop wins, `InputBindings.notched`); the flaps lever carries `detents` (raw per notch).
- Per aircraft data: `aircraft.json` `controls.flaps_lever` = `{"settings": [sim flap setting per lever notch], "on_ground": {"<notch>": setting}}` (A320: `[0, 1, 3, 4, 5]`, `{"1": 2}`); an aircraft without it sends notch i as setting i (the C172: FULL stays at 3). ### Aircraft data: FDM props

Aircraft whose `config.json` has the A320 shapes get extra FDM parts; absent keys = the C172's behaviour (asserted unchanged by the tests).
- `controls.flaps` a Dictionary with `detents` → `AirlinerControls` (`fdm/flight_controls_airliner.gd`): per-surface `SurfaceActuator`s from `controls.surfaces` (lag, rate, clip; aileron / elevator + = trailing edge down, rudder + = nose right, THS nose up = negative), flap and slat detents (slats lead an extension and flaps lead a retraction by 2 deg when a detent moves both), 5+5 spoiler panels, speedbrake. Ground spoilers extend above about 30 kt with the thrust levers at idle and stay out through a bounce until a lever is advanced. The Airbus law calls that spoiler mapping itself, then overwrites pitch, roll and yaw. The `law` seam: `FlightControls.law.update(dt, fdm)` writes `fcs.cmd` / `fcs.spoiler_cmd` and replaces the direct stick mapping.
- any `gear[].retractable` → `RetractableGear` (`fdm/gear_retractable.gd`, via `Gears.make(cfg)`): retract / extend over `controls.gear_transit`, locked down on the ground, nose wheel `gear[].steer {tiller_deg, pedal_deg, fade_mps, pedal_fade_mps}` (tiller fades by 70 kt, pedals hold ±6° until about 40 kt and fade by 130 kt), `gear[].brake_mu`, anti-skid, autobrake LO / MED / MAX (LO waits 4 s and MED 2 s after the ground spoilers deploy; the rates stay 1.7 and 3.0 m/s²).
- an engine with `thrust_table` → `EngineTurbineFadec` (`fdm/engine_turbine_fadec.gd`; limits from top-level `fadec_limits` through `fdm/turbine_fadec.gd`): JSBSim thrust tables over Mach and density altitude, N1 spool-rate tables, N2, EGT, TSFC x sqrt(T/288.15), start sequence, reverse. `engines[].orient_deg` gives the thrust line. Top-level `apu` adds `systems/apu.gd` (`fdm/apu_model.gd`).
- Expressions and 3-D tables: `fdm/expr.gd`, `fdm/table.gd`. `Aero.strict = true` makes an unknown property name an error (tests).
- **Props read** (`fdm/fdm_airliner_props.gd`): `controls/gear` `speedbrake` `autobrake` `tiller` `engine_master_<n>` `engine_mode` (0 NORM, 1 CRANK, 2 IGN/START) `reverse_<n>` `flex_temp_c` `lights/landing`, `failures/engine_fire[_<n>]`, `systems/hydraulics/antiskid`. The lever of engine n is `controls/throttle_<n>` − `controls/reverse_<n>`.
- **Props published:** `engines/<n>/{n1,n2 (percent),egt_k,ff (kg/s),oil,thrust_n,running,reverser,lever}` (engine 1 also as `engine/*`), `fdm/{mach,slat_deg,spoiler (per panel deg),spoiler_left_deg,spoiler_right_deg,speedbrake,stabilizer_deg,flap_lever,flap_deg,gear_pos,gear_state,door_pos,autobrake_on,ground_speed_mps}`, `apu/{running,starting,n_pct,ff_kgs}`.
- Saved and replayed: FlightControls `slat_deg slat_cmd spoiler spoiler_cmd speedbrake speedbrake_cmd gear_pos gear_cmd thrust_lever ground_spoilers`; gear `gear_pos gear_cmd gear_state door_pos`.
- Not modelled: engine feed from the pipe tanks (excluded from the default feed; `fuel.gd` feeds all tanks equally), bleed air, oil / fire systems.

### Aircraft data: flight control law (fly-by-wire)

`aircraft.json` `"fcs": {"law": "airbus_fbw", ...}` installs `FbwLaw` (`fdm/fbw_law.gd` + `fbw_{params,sense,pitch,roll,yaw,trim,protection,reversion}.gd`) as `FlightControls.law` of an `AirlinerControls`; absent = direct stick-to-surface control (the C172). Every other `fcs` key is optional and overrides `FbwParams.DEFAULTS` (nested dictionaries merge): `nz_max / nz_max_flaps / nz_min*`, `pitch_limit_deg`, `vmo_kt / mmo` (default from `limits.speeds`), `ground_blend_s`, `ground_gain` (direct elevator vs CAS kt), `flare`, and the groups `pitch` (`kn ki kq kiq q_max_dps trim_k trim_dead_deg k_alpha alpha_lead_s k_theta`), `roll` (`rate_dps kp ki kff k_bank hold_deg limit_deg limit_prot_deg taper_deg level_deg spoiler_start spoiler_max_deg`), `yaw` (`k_r k_beta limit_deg travel_kt`), `alpha_deg.rows` (`[slat, flap, alpha_prot, alpha_max, alpha_stall]` deg per configuration), `speed_prot`.

- **Laws** (`FbwReversion`): NORMAL; ALTERNATE (load factor law and auto-trim, roll direct, no protections); DIRECT (stick to surface, trim wheel). Reversion from `failures/{adr, adirs, elac (or elac_1 + elac_2), sec, hyd_g, hyd_b, hyd_y, fac}`: ADR / ADIRS / ELAC lost or two hydraulic circuits → ALTERNATE; ELAC + SEC or all three circuits → DIRECT; ALTERNATE with gear down → DIRECT; `fcs/law_force` (0..2) forces at least that law. `fac` only removes the yaw damper and rudder travel limit.
- **Pitch:** stick = load factor demand `cos(gamma) / cos(phi) + increment`, with the bank term capped at 33° (neutral = hold the flight path), rate loop with speed-scheduled gains (`q_ref / qbar`), THS auto-trim, ground mode = direct (scheduled gain) blended over `ground_blend_s`. Flare mode (normal law, gear down, levers back, below 50 ft RA): the pitch attitude is memorised, auto-trim stops, and from 30 ft that attitude is reduced by 2° over 8 s. Aft stick adds a pitch rate on top. **Roll:** stick = roll rate (15°/s), bank hold on release (a small bank is held; back to 33° above it), limit 67° (40° in the alpha / speed protections), roll spoilers on panels 2-5. **Yaw:** pedals with a speed travel limit, yaw damper, turn coordination.
- **Protections** (normal law): high angle of attack (stick maps to alpha between `alpha_prot` and `alpha_max`, alpha floor latch), high speed (nose-up bias up to 0.75 g above VMO + 6 kt / MMO + 0.01, forward stick gone by VMO + 16 kt), bank, pitch attitude (−15 / +30°), load factor (+2.5 / −1 g, +2 / 0 g with slats or flaps).
- **Props published:** `fcs/law` ("NORMAL" / "ALTERNATE" / "DIRECT"), `fcs/law_id` (0..2), `fcs/law_reason`, `fcs/ground_mode`, `fcs/flare`, `fcs/alpha_{prot,max,floor,stall}_deg`, `fcs/alpha_floor` (bool, for the A/THR), `fcs/stall_warning`, `fcs/prot/{alpha,speed,bank,pitch,nz}`, `ap/cmd/takeover`.
- **Autopilot interface:** with `ap/cmd/active` the law takes `ap/cmd/nz_g` (g increment) and `ap/cmd/roll_rate_dps` (+ right) instead of the stick; a sidestick deflection above 0.1 sets `ap/cmd/takeover` (the autoflight disengages) and gives the stick back at once.
- Tuned against `tools/a320_reference.json` (JSBSim A320): roll rate 7.4 / 15.3°/s for half / full stick (ref 7.35 / 15.0), alpha limits from the JSBSim tables; pitch is faster than the reference (63 % of a load factor step in about 1 s vs 1.9 s). Tests: `tests/test_fbw_a320*.gd`.

### Aircraft data: replay

Instant replay (R) records the C172 channel list (`systems/replay_layout.gd`, never changed, so C172 recordings keep their layout) plus the optional `replay` section of `aircraft.json` (all keys optional):
- `lerp`, `rad`, `deg`, `bool`, `int`: extra prop keys by kind (`rad` / `deg` are angles interpolated the short way; `bool` / `int` are held between frames).
- `enums`: `{"ap/fma/lateral": ["", "HDG", "NAV", "LOC"]}`: a string prop recorded as an index into its list (a value not in the list is not recorded).
- `units`: per-engine channels `engines/<n>/rpm | thrust_n | fuel_flow_kgs | egt_k | oil_press_pa | oil_temp_k | running` and `controls/throttle_<n>`, `mixture_<n>`, `starter_<n>`. Default: on when the aircraft has more than one engine. With more than two tanks every tank is also recorded as `fuel/tank_kg#<i>`.
- `fcs`: `true` (the list `ReplayChannels.EXTRA_FCS_FIELDS`: `slat_deg`, `spoiler`, `speedbrake`, `gear_pos`, `thrust_lever`, `ground_spoilers`) or a list of `FlightControls` field names; a field the aircraft's `fcs` lacks is skipped; an array field gets a channel per element. They play back like the elevator.

Taking control resumes every engine (rpm, running, EGT, oil, levers) and every tank from the replay frame. `tests/test_replay_generic.gd` pins the C172 channel list.

### Aircraft data: saved flights (the saveable rule)

A system node that keeps state between ticks (battery charge, APU, hydraulics, autoflight) joins the group `saveable` in `_ready` (`add_to_group(SituationSystems.GROUP)`) and implements `save_key() -> String` (stable name), `save_state() -> Dictionary` (JSON-safe) and `load_state(d)` (every key optional). `core/situation_systems.gd` then saves it with a flight (`systems.<key>` in the file); nothing else changes. Props under `engines/`, `ap/`, `apu/`, `fcu/` and `hyd/` are saved too. Optional FCS / gear fields (slats, spoilers, speedbrake, gear position) are saved when the object has them (names in `SituationFdm.OPTIONAL_FCS_KEYS` / `OPTIONAL_GEAR_KEYS`). Saves from before the hook (flat `soc`, `suction`, `fuel_line`, ...) still load.

### Aircraft data: model, cockpit, lights, audio

**Model textures** (the `models/*.png` the glb importer extracts): import them VRAM-compressed with mipmaps (`compress/mode=2`, `mipmaps/generate=true`; `compress/normal_map=1` for `*-normal`; `compress/high_quality=true` (BC7 / ASTC) for panels and placards with small text), never Lossless: a Lossless texture sits in video memory uncompressed (a 4096² normal map 64 MB, BC5 with mipmaps 22 MB). The atlases the livery and registration painters repaint (aircraft.json `texture` keys: C172 fuselage, wing, tail; A320 fuselage, engine) stay Lossless: the painted copy is an uncompressed texture anyway, and block compression would show in it. `tests/test_perf_settings.gd` checks the C172, the A320 exterior and the vehicles. When the cockpit glb repeats textures the exterior glb already has (the C172's panel, panel parts and interior atlases), set `import_script/path="res://aircraft/common/share_textures_import.gd"` in the cockpit glb's `.import`: on import it swaps each byte-identical `interior_<name>.png` for `exterior_<name>.png`, so the two models share one texture. The A320 cockpit panel textures (FCU, flight-deck panels, pedestal, radio) are still Lossless pending the overhead-text work.

Files are found by `AircraftDef.path(key)`: `models/exterior.glb`, `models/interior.glb`, `sounds/`, `panel.json` in the aircraft folder (override with a `files` map). Without an exterior glb a `PlaceholderAirframe` (`game/aircraft/placeholder_airframe.gd`) is drawn from `config.json` (wingspan, chord, tail arm, gear contacts, one propeller or nacelle per engine) with moving control surfaces. Generic code: `game/aircraft/common/`, `aircraft_model.gd`, `ui/instrument_panel.gd`. A320 named materials take roughness, metal and clearcoat from `MaterialFinish.table` (`aircraft/common/material_finish.gd`): fuselage paint 0.48 with clearcoat 0.22, nacelle paint 0.36 / metal 0.02 with clearcoat 0.16, inlet lip metal 1 / roughness 0.14, spinner metal 0.8. The fan blades are a separate dark metal stamp and do not take the cowl panel normal. Numbers are re-applied after the livery albedo swap, then the occlusion map (UV2) and panel-line normal (strength 0.65 fuselage, 0.55 engine). A roughness or metal PNG next to those maps (`exterior_panels_roughness.png`, `exterior_panels_metal.png`, and the engine, gear and interior pairs) multiplies the number; a missing file leaves the number as it is. cabin glass emits a warm dim glow from sun elevation, softer on the ground with the engines off (`MaterialFinish.cabin_glow`). The static fan-blur discs thicken with N1 (`FanBlur`).

- `model`:
  - `surfaces` `{pivot: {drive, sign}}`: glb node `pivot_<pivot>` turns about its X axis by `sign` x the control position (`drive` = `elevator`, `aileron`, `rudder` in radians, or `flap_deg`). `propellers` `[{pivot, engine (0 = engine 1), sign, visual_rate}]` (spin = `sign * rpm/60 * TAU * dt * visual_rate`; a turbofan's `rpm` is N1 percent: `visual_rate` about 0.75 for a fan, 0.13 for a propeller). Optional `origin_m` places the glb origin (default `metrics.vrp_m`). The glb uses FlightGear's frame (x aft, y right, z up from the origin). A missing pivot is skipped.
  - Airliner drives (`aircraft/model_drives.gd`): `slat_deg`, `stabilizer_deg`, `spoiler_<l|r><n>_deg`, `gear_pos` / `reverser` (0..1, with a piecewise `map` `[[value, degrees], ...]`), `nose_steer_deg`, `wheel_nose_rad` / `wheel_main_l_rad` / `wheel_main_r_rad` (rolling angle from ground speed; ignored below 0.05 m/s; uses the measured tyre radii). - Cockpit precision and placard sharpness (`aircraft/common/cockpit_precision.gd`, `cockpit_surface.gd`, `cockpit_precise.gdshaderinc`, `cockpit_surface.gdshaderinc`, both aircraft, fixed 2026-11-22). Render space has y = altitude, so in cruise the camera and the cockpit sit ~11 km from the render origin, where float32 steps are ~1 mm. Godot's single-precision renderer forms VIEW * MODEL on the GPU from those numbers, and the cockpit (overhead 0.6 m from the eye, displays 0.9 m) jittered: 2-9 px a frame on the overhead zoomed to 15 deg at FL350, 1-3 px on the C172 at 8,000 ft. Now, once the cockpit is built (deferred, after the FCU bars and LCD), every cockpit StandardMaterial3D becomes the matching cockpit shader (lit, lit alpha, unshaded, unshaded alpha: the same albedo / roughness / metallic / specular / AO / additive emission; anything else stays as it was), other cockpit ShaderMaterials get the line patched into a copy of their shader (same material object), each mesh gets its aircraft-local origin as the instance uniform `ckpt_origin` (refreshed when a lever moves it), and every frame the camera's aircraft-local pose (`CameraRig.cockpit_local`) goes to the globals `ckpt_view`, `ckpt_cam`, `ckpt_on` (`project.godot`). In the cockpit camera's own pass the shader takes the translation from those small numbers; shadow passes and other cameras keep the engine's. StandardMaterial3D stays the object other code writes to: `CockpitSurface.sync` copies albedo and emission each frame they change. Samplers filter anisotropically (the overhead is seen at a grazing angle), and display quads average four taps across the pixel (a SubViewport has no mipmaps, so PFD/ND text shimmered from the seat). `cockpit.detail_textures` `{material name: path}` swaps in a higher-resolution copy of a glb atlas with the same UV layout on every preset but Low: the A320's legend overlay `a320_fd_glare` (every panel, overhead and pedestal placard) uses `models/interior_fd_glare_4k.png` (upstream 4096 px, written by `tools/24_a320_textures.py`; BPTC / ASTC with mipmaps, 22 MB on the GPU), and the 2048 px `interior_fd_glare.png` / `interior_fd_main.png` are VRAM-compressed too (5.6 MB each instead of ~22 MB), so the cockpit uses less GPU memory than before on every preset. The cockpit eye's seat dip (`CameraMotion.seat_step`, 2.8 cm per g, ~1.2 Hz) shrinks with the zoom (`CameraMotion.cockpit_eye`: x fov / 70), so a 2 mm bob no longer sweeps a 15 deg view of a panel. `--cockpit-precision=off` keeps the glb materials (A/B checks). Measure: `godot --path game res://tests/debug_overhead_shake.tscn --audio-driver Dummy -- --aircraft=a320 --airport=VABB --air=35000 --air-kt=250 --view=cockpit --turb=0.6 --fov=15 --frames=120 [--still] [--ahead] [--shots=<abs dir>] [--cockpit-precision=off]` (C172: `--aircraft=c172 --air=8000`; `--still` holds the seat dip at 0). Tests `tests/test_cockpit_precision.gd`.
- `audio`: `engine` and `wind` mappings (volume / pitch against rpm and airspeed; keys and defaults at the top of `common/aircraft_audio.gd`). The wavs come from `sounds/`; a missing file is silent. An `audio` with a `layers` list (the A320 pack; draft `game/aircraft/a320/audio_section.json`) uses the data-driven layer engine (`common/audio_layers.gd`, pure curve / gate / trigger functions in `common/audio_curves.gd`, schema in that header): each layer is `{file, bus, loop, drive, volume, pitch, gain, view, muffle_hz, per_engine, gate, trigger}`. `drive` is a Props key (`engines/{n}/n1`) or `[op, ...]`; `volume` / `pitch` are `[[x, y], ...]` tables; `per_engine` makes one copy per engine panned left / right; `gate` conditions (view, ground, props, min / max, in-transit `between`, `moving`) and `trigger` edges (rising / falling / change) fire one-shots; the cockpit view low-passes layers with `muffle_hz` and applies the `view.cockpit` factor. `file` may be a `res://` path to reuse another aircraft's sound. A320 sources: `game/aircraft/a320/sounds/SOURCES.md`, rebuilt and audited by `tools/25_a320_sounds.py` (`--fetch`, `--build`, default audit). The engine layers are the jet recordings. Flaps and slats use the hydraulic-pump whine while they move, spoilers use the airliner landing-roll buffet, and the gear lock is the pump starting. The gear-transit loop is the hoist recording. `"gpws": true` (the A320 only) adds `common/gpws_player.gd`: a looping stall horn while `fcs/stall_warning` or `fdm/stall_warning` is set, and one-shot beeps for a radio-altitude call (500, 100, 50, 30, 20, 10 ft, once per approach), sink rate (below 500 ft and steeper than −1000 ft/min, at most every 4 s) and a rising edge of `ap/cmd/takeover`. The cue rules are pure in `common/gpws.gd` (feet and ft/min, the same units as the instructor callouts). The tones are generated by `tools/a320_tones.py` and play in normal flight; the instructor callouts stay off unless the pilot turns them on. The C172 leaves `gpws` unset and keeps its own stall horn.

### Aircraft data: livery (paint colours)

The pilot-chosen paint colours are data: `aircraft.json` `"livery"`. The C172 masks come from `tools/25_livery_masks.py` (`tools/.venv/bin/python -I tools/25_livery_masks.py [--preview <dir>]`; `--preview` writes colour overlays of the masks). The A320 masks come from `tools/25_a320_livery_masks.py` (fuselage, fin, cheat line, engines; wings stay out). Logic: `aircraft/common/livery.gd` (`Livery`, pure); stickers: `livery_stickers.gd`; pictures and presets: `livery_store.gd`; GPU pass: `livery_paint.gd` + `livery.gdshader`. Plan: `docs/LIVERY-PLAN.md`. On the start screen, **Livery** (key **2**) is the step after Aircraft: swatches and a colour picker per region, a picture per sticker slot, Save / Load preset and Reset. Presets stay on this computer (`user://liveries/<aircraft>/<name>.json`). `--livery` still sets colours for a command-line flight.

- **Section:** `atlases` `[{id, texture}]` (exterior atlases that carry paint, path relative to the aircraft folder), `regions` `[{key, label, default [r,g,b] 0..1, masks [{atlas, mask, luma}]}]` and optional `stickers` `[{key, label, atlas, box [x,y,w,h], mirror_box?}]`. A region may be on several atlases (the C172's blue is on three), each with its own mask PNG; one `key` is what the pilot picks. `mask` is an 8-bit grey PNG of the atlas size (0 untouched, 255 recoloured, soft edges) in `livery/<atlas>_<region>.png`. `luma` is the mean Rec.709 luminance (sRGB, 0..1) of the atlas under the mask at full strength (>= 242): the shading reference. At most 4 regions per atlas (shader slots). A sticker slot is a fixed box; `mirror_box` is the other side. Unknown or malformed parts are ignored (`Livery.parse`); no section = no livery.
- **C172 regions:** `body` (white paint: fuselage, wing, fin, tailplane, wheel fairings), `accent` (the blue: nose and cowl, side sweeps, deck stripe, wing-tip caps, fin and tailplane stripes), `stripe` (grey pin stripe), `struts` (optional: white wing struts and main gear legs, fuselage atlas only; the nose gear leg is bare steel and stays). Kept out of every mask: tyres, propeller, spinner, hub, lamps, glass, antennas, the baked "Cessna" logo and "SKYHAWK" glyphs, and the registration boxes. Masks come from colour thresholds inside island rectangles (lists at the top of the tool); a new aircraft with a paint layer needs its own. They derive from the GPL-2.0-or-later c172p atlases (`third_party/c172p/SOURCE.md`); no repo texture changes, the recolour is made in memory.
- **A320 regions:** `body` (fuselage tube only), `fin` (fin and rudder), `cheat` (the slate cheat line), `engines` (the nacelle atlas). Wings, slats, flaps, ailerons, spoilers and the tailplane stay the factory white: wing top and bottom share UV space, so they are not a region. Masks are derived from the shipped atlases and the UV islands of `exterior.glb` (`tools/25_a320_livery_masks.py`). Both registration rectangles stay out of every mask.
- **Choice and rule:** the choice is `{region key: "#rrggbb"}`. `Livery.colors_of(lv, stored)` merges it over the factory colours (bad hex and unknown keys ignored), `Livery.is_identity` = nothing to paint, `Livery.cache_key(aircraft_id, colors, stickers)` is the texture cache key (bump `KEY_VERSION` when masks or the rule change). An empty sticker map leaves the key exactly as it was before stickers existed. Rule (sRGB as stored, Rec.709 luma): `out = lerp(orig, colour * clamp(luma(orig) / luma_base, 0, 1.3), mask)`, alpha kept, channels capped at 1, so baked occlusion, panel lines and dirt survive. Where regions meet the weights are added up and each takes the luminance left after the others' share (`Livery.recolor_multi`), so edges have no dark halo. A very bright colour on a bright paint saturates a channel; a region at factory colour still goes through the shader and can differ by about 1 %.
- **`LiveryPaint.compose(host, def, atlas_id, atlas, colors) -> Image`:** awaits one drawn frame and returns an RGBA8 image of the atlas size without mipmaps (the caller stamps the registration, then `generate_mipmaps()` and `ImageTexture.create_from_image`), or `null` = use the original (factory colours, no region on this atlas, mask missing or wrong size, no pixels on the dummy renderer / headless).
- **Stickers:** the pilot's entry is `{slot key: {image, scale, dx, dy, mirror}}`. `image` is a file name in `user://liveries/images/`, never a path (`LiveryStickers.sanitize` strips directories). Load accepts PNG, JPG or WebP up to 4 MB, scales the long side to 512 and re-encodes PNG (the sha1 of those bytes is the file name). `scale` 0.25..1 contains the picture in the slot box; `dx` and `dy` -1..1 slide it in the leftover slack; `mirror` draws it flipped in `mirror_box`. `LiveryStickers.stamp` blends it after the colour pass.
- **Setup:** `Session.setup.livery` = `{<aircraft id>: {colors: {region key: "#rrggbb"}, stickers: {slot: {...}}}}`, saved in `last_flight.json` and in an F11 quick-save. Loading that save repaints the aircraft when the colours differ from the paint already on it. A replay writes flight-model state only, so it does not reset the paint. A missing entry = factory. A dark region colour no longer brightens the lighter tip of a stripe. The C172 nose leg and the A320 tailplane are not in any mask, so they stay the atlas colour. `Livery.repair_setup` drops what it cannot use (not a dictionary, unknown aircraft or region, bad hex), writes lowercase hex, never raises, and keeps a stickers dictionary that still has a field after sanitize. `Livery.entry(all, id)` is the safe read. Presets are the same entry shape, one JSON file per name, and are not copied into the repository.
- **Command line:** `--livery=body=#c8101a,accent=#f2f2f2,stripe=#26262b,struts=#f2c200` (a bare `rrggbb` also works); per aircraft: `--livery=c172:body=#c8101a,a320:fin=#102030` (`Livery.parse_cli`; bad items and unknown regions skipped). It is a flight option: the start screen is skipped, nothing is saved, and a command-line flight starts from the factory livery.
- **One pass per atlas** (`aircraft/common/paint_pipeline.gd`, `PaintPipeline.apply`, called by `AircraftModel._build_glb`): base atlas → livery recolour (only if a region on that atlas differs from factory) → stickers (`LiveryStickers.stamp`, on the recoloured copy, or on a copy of the atlas when the colours are factory) → registration (wipe the old number, stamp the new one) → `generate_mipmaps` → cached `ImageTexture` → surface override on every exterior surface using the atlas. **The order is fixed:** number boxes are outside every mask and the wipe reads the recoloured rows, so the number sits on the new paint; mipmaps last. After an override a surface no longer shows its atlas path, so a second painter would find nothing. The start-screen turntable (`ui/menu/livery_preview.gd`) paints the same way without hiding the model and without stamping the call sign. It keeps the recoloured atlas and restamps a picture on the next frame when the picture, scale, offset or mirror changes; a change that arrives while a paint is in progress is not dropped. A colour change runs the GPU compose once, with a loader on the model while that frame draws. The compose viewport is parented to the scene root: the turntable is a `SubViewportContainer` and would otherwise shrink the atlas to the page, which drops the picture off the model. The preview copy of the atlas is mipmapped (long side 2048), and the viewport matches the panel, so a colour stays a solid region instead of aliasing into stripes. Drag orbits the model (a mild 32° lens, framed to the aircraft); the scroll wheel or the + and − buttons zoom it (about 0.55× to 3.4×); Side, Front and Tail frame that part. The colour swatches are fixed squares in their own scroll column. Headless, the page shows a note and does not load the model.
- **Cache** key `aircraft | TEXT | atlas | livery key` (`factory` when that atlas is untouched): a new colour, sticker or call sign repaints, a setup seen before does not, a colour not on an atlas never repaints it. At most 9 textures are kept (about 22 MB each with mipmaps; an A320 atlas is larger). Nothing is painted when the livery is factory, there is no sticker, and the registration is the number the atlas carries (`registration.baked`; the C172's default VT-LBR is not baked, so it is repainted).
- **While painting:** the exterior is hidden for the frames the GPU needs (a one-shot SubViewport per atlas and glyph style); a 12 s watchdog shows it again. A headless run does not paint; a renderer that returns no pixels keeps the factory atlas.
- **Tests and probes:** headless `tests/test_livery.gd`, `test_livery_struts.gd`, `test_livery_a320.gd`, `test_livery_builder.gd` (preset round trip, import limits, sticker fit), `test_paint_pipeline.gd` (GPU compose and glyph render replaced by `PaintPipeline.test_compose / test_glyphs`), `test_livery_session.gd`, `test_registration.gd`. The menu suites cover the Livery step. Windowed (window in front; an occluded window is not drawn on macOS):

```bash
~/.local/bin/godot --path game --windowed --resolution 800x600 --audio-driver Dummy res://tests/debug_livery.tscn -- --out=<dir> [--aircraft=c172] [--liveries=red,navy] [--views=front] [--no-checks]
~/.local/bin/godot --path game --windowed --resolution 960x600 --audio-driver Dummy res://tests/debug_livery_flight.tscn -- --out=<dir> --livery=body=#c8101a,accent=#f2f2f2,stripe=#26262b,struts=#f2c200 --callsign=VT-LBR --airport=VAJJ --clean --quality=low [--air] [--factory]
```

The first prints `LIVERY PROBE PASS|FAIL` lines (factory returns null; mask-0 pixels identical; registration boxes untouched; GPU equals `Livery.recolor_multi` within 2 levels) and saves atlas crops and 3/4 renders. The second runs the real flight scene, checks the painted fuselage atlas against the original and the masks, saves front / rear / fuselage-side / wing-underside shots and prints `LIVERY FLIGHT PASS|FAIL`; with `--headless` it checks that the factory look stays and nothing hangs.

### Aircraft data: displays

Glass-cockpit aircraft (the A320-family one) draw their screens in code from Props, through the same panel pipeline as the steam gauges (SubViewport, 3D quads, click forwarding).

**panel.json schema** (new keys optional; the C172 file uses none and its rects are unchanged, asserted in `tests/test_displays.gd`):
- `size [w, h]`: natural size in px; without it the grid size is used, enlarged to hold every `rect`.
- Any item (`gauges[name]`, `strip`, `radios`, `switches`): `rect [x, y, w, h]` in px instead of `cell`; `span [cols, rows]` of grid cells (gauges; `strip` had it already).
- `gauges[name].kind: "display"`: the script is a full-rect `Display` (`ui/displays/display.gd`) that scales its own drawing (its `design` size) into the rect; otherwise a round `Gauge`. Item names (`pfd`, `nd`, `ewd`, `sd`, `fcu`, `mcdu`) are what `cockpit.spots` and the `overlay` layouts refer to.
- Example: `game/aircraft/a320/panel.json`. Preview and screenshots: `godot --path game res://tests/debug_displays.tscn --audio-driver Dummy` (PNGs to `$FREESIM_SHOTS`).


**Shader baker** (Godot 4.5+, `shader_baker/enabled=true` in every preset of `game/export_presets.cfg`, checked by `tests/test_shader_baker.gd`): the export compiles the game's shaders into the `.pck` (SPIR-V for Vulkan, Metal's MIL on macOS), so a fresh install skips that work on its first start and the first flight has fewer compile hitches. The GPU driver still builds its own pipelines from them, so this shortens the first start but does not remove every hitch. What the exporter needs:
- **A GPU and a window.** Godot cannot bake under `--headless` (it silently exports without baked shaders). `make_release.sh` therefore exports windowed (a short editor window opens, `--audio-driver Dummy`); on a build machine without a display or GPU run `HEADLESS=1 tools/package/make_release.sh` (unbaked packages, they still work).
- **The Forward+ renderer**, the one the packages start on: the baker includes the core shaders only for the renderer the exporting editor runs, so the script passes `--rendering-method forward_plus`. Low / Medium players run Mobile, whose shaders are not in the bake: they compile on the first start as before and Godot caches them afterwards. Godot cannot bake two renderers into one `.pck`.
- **No `game/override.cfg` during the export.** It is this checkout's own renderer choice. Godot 4.7 loads it into the project settings, so without `--rendering-method` the exporting editor would run (and bake) Mobile. The script moves it aside and puts it back afterwards. The windowed editor also re-saves `game/project.godot` in its own format (comment header, default values such as `renderer/rendering_method="forward_plus"` dropped; same meaning, but `tests/test_graphics_presets.gd` reads that line), so the script restores that file too. After a manual windowed export, check `git diff game/project.godot`.
- **The right host for each driver.** Each preset bakes for its platform's `rendering/rendering_device/driver` (project defaults: Linux Vulkan, macOS Metal, Windows Vulkan). A macOS editor can bake Metal and Vulkan, so `make_release.sh` on a Mac bakes both packages; a Linux editor bakes Vulkan only, so the macOS package built on Linux has no baked Metal shaders. A Windows preset left on Vulkan can be baked from macOS or Linux; Direct3D 12 needs a Windows editor.
- **macOS packages, two limits** (seen in a test export from macOS 27 with only the Command Line Tools): (1) without Xcode's Metal toolchain (`xcrun -f metal` must work: full Xcode, then `xcodebuild -downloadComponent MetalToolchain`) Godot warns "Metal shader baking limited to SPIR-V" and the Mac still builds the Metal libraries on first use; (2) the macOS preset targets macOS 14 (`application/min_macos_version_arm64` and `_x86_64` = 14.00, chosen 2026-11-18) because the Forward+ scene shader, volumetric fog and FSR2 need Metal Shading Language 3.1 (macOS 14); at 11 Godot left them to be compiled on the player's Mac. Macs on macOS 11-13 cannot run the game. Before a release build, install full Xcode and run `xcodebuild -downloadComponent MetalToolchain` so `xcrun -f metal` works.
- Export templates as below (the baker itself needs nothing more). Exports take longer and the `.pck` grows by a few MB (test export: 79 baked files, 2.1 MB, Linux / Vulkan; 86 files, 5.7 MB, macOS / Metal).

## 5. Aircraft models and 3D scenery

**The aircraft** is the FlightGear c172p model and cockpit (GPL-2.0-or-later, c172p team), converted by the Blender scripts in `tools/blender/`; the original sources are in `third_party/c172p/`. The live gauges are drawn onto the real panel at each instrument's true position. Without the `.glb` files the sim falls back to a box placeholder.

**3D buildings** (578k OSM footprints; heights from OSM tags or an estimate by footprint size; streamed within 9 km, hidden above 2500 ft AGL; scene `city_district`):
- **Geometry** (`tools/building_geom.py`, written by `10_buildings.py` as BLD2): flat roofs of 90 m² and more get a sloped parapet strip; small 4-corner footprints (under 150 m², up to 7.5 m) get a hip roof (30 % in the Mumbai-Pune grid, 75 % in the Konkan-Kerala corridor); big flat roofs get a stairwell box (from 250 m²) and a hexagonal water tank (from 400 m²). A BLD2 vertex carries wall height (cm, 16 bit), a parapet / rooftop-kind byte and the height fraction, besides roof colour and a style byte (`pid << 2 | roof type`). `Buildings` still reads old BLD1 tiles.
- **Shader** (`world/building.gdshader`): a hash of the building seeds wall colour, window rhythm, floors (3.1 m), slab edges, sills, balconies, shopfronts on the ground floor of medium buildings, glass curtain-wall towers above 32 m, dirt, soot and rain streaks; roofs: bare concrete, white coating, brick, tarpaulin or the satellite colour. The window pattern fades with the pixel footprint; the average glass tone stays out to the draw distance, and a dark band at the base seats each wall on the ground within about 1.6 km. Windows light up at night. Buildings cast and receive the cascaded sun shadows. Researched terminals without a landmark model (roof type 2, `tools/terminal_ref.py` `facade_look`) use `world/building_terminal.gdshaderinc` (reference cladding, glazing share, roof colour, evenly lit hall at night; `docs/TERMINALS.md`). Its per-panel glass tone fades with the pixel footprint like the mullions; once e610670 dropped the far fade, that tone sparkled across distant facades as the camera moved.

**Water:** the Arabian Sea, creeks, rivers and lakes (elevation data and OSM water polygons) use an animated surface with wind waves, sun glints and Fresnel sky reflection; shallow creeks keep the satellite tint.

**Clouds:** a raymarched volumetric cumulus layer at the configured base and cover. It reads scene depth, so you can fly under, through (fog inside) and above it. It drifts with the wind aloft and is lit by the sun (darker bases, warm tints at sunset). High and Ultra march that layer at half resolution and blend it with the previous frame; Max marches at quarter resolution. Low and Medium stay a full-resolution march. A camera jump past 50 m, or a turn past 20°, drops the history for one frame. The low-res march is not jittered, and the upscale converts the reversed depth buffer to the camera's clip space; a surface nearer than the cloud layer (the cockpit frame, the aircraft below the deck) gets no cloud. Before, the horizon and the windshield frame blinked and the frame edge showed low-res steps. The full-screen quads keep their order by material priority (heat shimmer -10, clouds and the upscale blit `CloudLayer.PRIORITY` 10, sun glare 20): by distance alone the cloud blit drew first on Max and the shimmer painted the cloud-free screen copy over it, dark discs behind the engines. `tests/debug_flicker.tscn` saves a burst of frames from a flight (`--setup=<last_flight.json>`, `--view=`, `--roll=<s>` for a takeoff roll, `--air=<kt>:<ft>` for an air start, `--opt=<key>:<on|off>` for one option this run, `--push=on` to start the pushback, `--thrust=<0..1>` for a run-up on the brakes, `--cam=f,r,u:af,ar,au` for a free camera placed relative to the aircraft) to measure blinking. Saving a frame each frame slows the game to a few fps, so a timing glitch needs a real-time screen recording (`screencapture -v`).

**Motion blur in the cockpit:** in the cockpit view nothing nearer than the airframe's cutoff is blurred (`PostFxRules.blur_near_param` passes a negative near cut; `motion_blur.glsl` leaves those pixels alone). The renderer's velocity buffer carried a whole frame of the aircraft's travel on the cockpit about every 10 frames, and at speed the panel smeared for one frame every ~0.4 s. Outside views keep the aircraft's own motion. **Motion blur on scenery** (fixed 2026-11-17): in steady flight on High and up the blur smeared built-up areas. Two causes, both measured in the real chase view: the renderer's velocity for the OSM building meshes was about 100x the real motion (12+ px of blur on 10 % of the frame; hiding the buildings removed it), and the shader converted depth as GL ndc `1 - 2d` although the projection it gets already uses the renderer's reverse-Z [0, 1], so the whole ground read under 50 m (the camera reprojection came out far too large and every pixel counted as near the aircraft). Now depth is read as is, and each scenery pixel's motion is capped at `(turn px + travel x focal / distance) x 1.5 + 0.5` (`MotionBlurEffect.camera_motion_px`, `capped_px` in `motion_blur.glsl`): false blur fell to 0.3 % of the frame and steady flight matches blur off, while real camera turns still blur. `tests/test_post_fx.gd`. A changed `.glsl` needs a Godot import (`godot --headless --path game --import`, or `./run.sh`) before a direct run uses it.

(FPS figures are from before the cascaded shadows and Forward+ and have not been re-measured.)
- **Render resolution** (Options > Graphics, `ui/menu/resolution_row.gd`, `core/render_resolution.gd`): Auto, or a fixed size listed for the screen the window is on (native, 2560×1440, 1920×1080, 1280×720 ... in the screen's own shape, each with its share of the frame). Only the 3D world is drawn at that size; the window, menus and HUD stay native, and below native Forward+ upscales with FSR2. Saved in `graphics.cfg` as a share of the frame height (`render_frac`, 0 = Auto), so it carries to another display. When the window moves to another screen or is resized, the sim applies the settings again within a second and the list rebuilds.
- **Auto render resolution** (Render resolution "Auto"; `core/render_scaler.gd`): the same rule on every machine, no brand, processor or OS checks (`tests/test_graphics_presets.gd` fails if the graphics code names one). The 3D world is drawn at the preset's scale; the main viewport's GPU time (`RenderingServer.viewport_get_measured_render_time_gpu`) is averaged over 1.5 s against the screen's frame budget (1000 / refresh rate ms, 60 Hz if unknown). Above 92 % of the budget the scale steps down by 0.1, never below 0.7; under 65 % for 6 s it steps back up, never above the preset's. Only the viewport scaling is redone on a step. Below 1 Forward+ upscales with FSR2 and switches the edge filter and TAA off (FSR2 antialiases; a filter on top of it only softened the picture again); Mobile stays bilinear. A fixed Render resolution choice replaces Auto. **Without a GPU time** (the driver reports 0: Metal in Godot 4.7 has no GPU timestamps, so on a Mac Auto never acted before) the frame time stands in (`RenderScaler.feed_any`), again the same rule everywhere: only whether a GPU reading exists decides. With vsync on, a frame that kept its refresh slot (at most 1.15 × the budget) says only "fast enough" and counts as 80 % (no step either way); a frame past it missed its slot and counts as it is; one frame counts at most 2 × the budget, so loading hitches do not step down. With vsync off the frame time is the load. With vsync on there is no headroom reading, so after a step down one step up is tried once 98 % of the frames have kept their slots for 20 s; a step down within 10 s of that try doubles the wait (up to 160 s), so a scale that cannot hold is retried a few times in ten minutes, not every few seconds. Limit: a CPU-bound machine without GPU timing also steps down (to 0.7 at most), which does not help it. Tests: `tests/test_perf_settings.gd`. This replaced a budget that, on base Apple chips only, drew every preset at 70 % with FSR2 plus FXAA and cut clouds, MSAA and shadows: on High and Ultra that read as a blurry picture. `core/render_budget.gd` now only finds the window framebuffer. The Thrustmaster Captain Pack is two pads, and each bound axis reads that list once a frame (`input/joy_pads.gd`) rather than asking for every control.
- Each preset names its renderer (`core/graphics_settings.gd`, `renderer` key). Low and Medium run on Mobile (fastest on integrated GPUs); High, Ultra, Max on Forward+, the project default. Picking a preset on the other renderer writes `override.cfg` (git-ignored), and Options and F10 show "Restart libresim to apply". Godot only picks the renderer at start, so the change cannot apply live: a change the player makes (preset or renderer switch) asks **Restart now?** (`ui/menu/restart_prompt.gd`). **Restart now** relaunches libresim with the same command line minus an old `--rendering-method` (`core/renderer_restart.gd`, `OS.set_restart_on_exit`); in flight the situation is saved first as `user://saves/_renderer_restart.json` and resumed straight after (`--resume-flight=`, start_screen.gd), then that save is deleted. **Later** keeps the note. The automatic first-start renderer choice does not ask. `tests/test_renderer_restart.gd`. The F10 Renderer toggle overrides this until the next preset change. On the first start without `override.cfg`, a saved Low / Medium preset writes Mobile. A `--quality=<preset>` run never saves a renderer (it is a one-off: add `--rendering-method mobile` or `forward_plus` for that run), and tests and probes never write the file; only a normal run that picks a preset or uses the renderer toggle does. Delete `game/override.cfg` to go back to the project default.
- Forward+ adds SSAO (High+), SSR on water and wet runways plus TAA (Ultra+), SSIL (Max), FSR2 below render scale 1 (Mobile stays bilinear; it has no FSR), and more real apron floodlight lamps (2 / 4 on Low / Medium (Mobile: never more than 4), 10 / 16 / 24 on High / Ultra / Max).
- **Edge smoothing** (`core/screen_aa.gd`, preset key `post_aa`; Options > Graphics "Edge smoothing": Auto / SMAA / FXAA / Off, UserOptions `edge_smoothing`): every preset smooths edges with SMAA 1x whenever no temporal method runs, so Low, Medium and High (and Ultra / Max on Mobile, which has no TAA). TAA (Ultra, Max) and FSR2 (Forward+ below render scale 1) smooth edges themselves, so the filter is then off: never two post AA passes. SMAA replaced FXAA (Low / Medium) and nothing (High): it finds edges by colour and blends along them, keeping texture detail (runway paint, building windows, instrument text) that FXAA blurs. Godot runs it before the bilinear upscale, so its cost follows the render scale. Measured GPU cost at 1920×1080 on an Apple M4 only (MoltenVK timestamps, `GPU_PROFILE=1`): about +0.2-0.3 ms over FXAA on Low and Medium, +0.5 ms over no filter on High; three light full-screen passes, so other GPUs should scale with their fill rate. Auto uses the preset's filter; a fixed choice applies at once to every preset. An `options.cfg` without the key, or with an unknown value, reads as Auto. Works on the Forward+ and Mobile renderers with Vulkan, Direct3D 12 and Metal; the Compatibility (OpenGL) fallback ignores screen-space AA and keeps only MSAA. `--aa=smaa|fxaa|off` forces a filter for one run (benches, before / after shots; `AA=` in `tools/bench.sh`); TAA / FSR2 still win. Edge-detection threshold: Godot's default 0.05 (`rendering/anti_aliasing/quality/smaa_edge_detection_threshold`). Tests: `tests/test_screen_aa.gd`.
- **Ground helper maps** (`world/terrain_helper_maps.gd`, used by `TerrainTileCache._load_t` on the worker): the land-class (R8: 255 water, 1..200 tree density, sampled bilinear), WorldCover (R8 class, read with texelFetch only) and shore-distance / openness (RG8, bilinear) maps keep their full 768² on level 0 (7.68 km tiles: the ground within about 10 km, where the detail textures, sand, shore foam and canopy edges are drawn) and half size (384²) on the coarser levels, drawn beyond that, where the satellite image carries the look. Land class and WorldCover shrink by nearest texel (no class ID is ever blended into another), the shore distance bilinear. A coarse tile's helper maps drop from 2.36 MB to 0.59 MB. The files on disk are unchanged (no pipeline re-run). CPU copies (`landclass_at` / `worldcover_at`, read by trees, ground cover and the ground checks) are kept only for level-0 tiles, or the coarser tile standing in where level 0 has no mask (`TerrainHelperMaps.cpu_source`). Packing land class and WorldCover into one RG8 texture was left out: it saves no bytes (the same two bytes per texel) and land class needs bilinear sampling where WorldCover needs nearest. Measured on Apple M4 only (C172 at VABB runway 27 after loading, Godot monitors): ground tile textures Low 479 → 228 MB, Medium 539 → 250 MB, High 640 → 313 MB; total video memory Low 1298 → 1040, Medium 1718 → 1405, High 2529 → 2200 MB; RAM (static) Low 656 → 405, Medium 680 → 395, High 803 → 469 MB. An A320 at 130-175 kt for 150 s had the same 3 frames with tiles pending (at most 4) before and after. Screenshots of coast, farmland, forest and city at Low and High: `review_screenshots/perf/fix14/`. Tests: `tests/test_terrain_helper_maps.gd`.
- **Scenery per preset** (`world/scenery_quality.gd`, applied with the preset): the ground tile cache keeps at most 120 (Low) / 150 (Medium) / 400 (High and up) tiles per kind (heights, images, composites) before it trims those unused for 3 s (`TerrainTileCache.max_entries`). A level-0 image tile is about 2.6 MB of video memory (768² imagery plus land-class, WorldCover and shore maps) and a coarser one about 0.9 MB (helper maps at half size, below), so a long flight could grow an uncapped cache to about 1 GB; the tiles in view are never trimmed (the quadtree picks tiles by distance, not view direction, so turning reloads nothing; flying back over ground left more than 3 s ago reloads it, showing the coarser parent tile until then). Terrain nodes cast sun shadows on High and up only; Medium's one 700 m split would spend a whole terrain pass on relief shadow the eye barely sees. Medium dropped MSAA 2× (SMAA stays) and draws its shadows with one split on a 2048 atlas. Measured on Apple M4 only (MacBook Air, 1920×1080, other Godot runs sharing the machine, so frame times are noisy): Medium GPU time at a pinned 70 % (MoltenVK) 20.3 / 24.9 / 20.9 / 22.2 → 20.4 / 20.0 / 19.9 / 18.2 ms at the VABB final and 27.5 / 23.7 / 28.6 / 22.7 → 24.4 / 22.7 / 19.6 ms in the Ghats chase; an earlier quieter A/B measured MSAA alone at 32 → 18 ms and Medium shadows at 9 ms. Video memory after loading at VABB (C172, Medium, Godot monitor) 2078 → 1696-1709 MB (with the compressed model textures; A320 2152 → 1906 MB); triangles drawn 4.57 M → 3.43 M (no terrain in the shadow pass). Building shadows stay on: the noise was larger than any difference. Thin edges: SMAA keeps most edges smooth; near-horizontal curves (the glareshield) show slight steps in still frames (`review_screenshots/perf/`); shimmer in motion was not measured. Tests: `tests/test_perf_settings.gd`.
- Every preset sets the sun shadow atlas size and the soft-shadow filter quality at run time. Anisotropic filtering is 16× (project setting). Clouds take `cloud_light` light samples per step (`CloudLayer.light_steps`).
- **Draw distances and stand-ins** (graphics Phase 2; `world/vis_ranges.gd`, `vis_chunks.gd`, `jetway_standin.gd`, `hlod_director.gd`): airport dressing (ground vehicles, stand paint and numbers, stand boards, terminal signs, control towers, apron lamp masts and frames) is drawn only while it covers at least 3 px of a 1080p frame at a 60° view: range = size x 540 / tan(30°) / 3, size = the square root of the object's largest face. The preset scales it with the terrain LOD ladder (`lod_k` / 1.6: Low 0.75, Medium 0.875, High 1, Ultra 1.25, Max 1.5; hook in `Graphics.apply_to_scene`), and a narrow camera (tower, fly-by, telephoto) stretches it by tan(30°) / tan(fov / 2) in 1.25x steps. Ranges fade over ±5 % on Forward+ (a fading object is drawn unbatched in the transparent pass: ±12 % cost about 10 % more draw calls at VABB, ±5 % about 3 %); the Mobile renderer in Godot 4.7.2 draws no range fades, so on Low / Medium an object switches off at the pixel limit. Lamp masts are built per 400 m cell so each cell has its own range. Jetways beyond about 660 m (16 px) become one box over the raised tube in the bridge's seen colour (its parts use the box as `visibility_parent`, cross-faded on Forward+), and the box goes at the 3 px limit. A jetway out at the player's aircraft is always drawn in full (`VisRanges.pin`). Not ranged: terminal models (landmarks, one cheap mesh each), windsocks (a pilot looks for them), light points, apron light pools and lit windows (the night look from afar), city buildings and trees (they stream by radius already). `--no-vis-ranges` turns it all off for before / after runs; `--vis-fade=<share>` sets the fade band for a measurement (0 = no fade).
- **Occlusion culling** (`project.godot` `rendering/occlusion_culling/use_occlusion_culling`; `world/occluder_build.gd`, `occluder_rings.gd`, `occluder_jobs.gd`, `occlusion_rules.gd`): each landmark terminal gets occluders made at load time on a worker thread from its own walls (wall panels chained into footprint rings, moved 1 m inside the building; open walls keep to the wall surface with 1 m trimmed off each edge), so an occluder never hides what the building does not. Godot rasterises occluders on the CPU every frame (Embree), so it runs only while the camera is within 150 m of the ground (off again above 250 m) and an occluder is loaded (`HlodDirector` switches the main viewport's `use_occlusion_culling`). City buildings get no occluders: each is part of a 7.7 km tile mesh that can never be hidden whole. `--no-occlusion` (no occluders, never on) and `--occlusion-always` (any height) are for measurements. Tests: `tests/test_hlod.gd`, `tests/test_occlusion.gd`; numbers in `docs/GRAPHICS-PLAN.md` "Phase 2".
- **Ground particles** (graphics Phase 3; `world/ground_fx.gd` under `TouchdownFx/Ground`, `ground_emitter.gd`, `ground_fx_look.gd`, `rain_splash.gd`, `wheel_spray.gd`, `engine_wash.gd`, `ground_surface.gd`, `rain_ripples.gdshaderinc`; counts per preset in `world/ground_fx_quality.gd`): **rain rings** on wet runways, taxiways, aprons and puddles within 45 m of the camera (a normal tweak in `runway_v2.gdshader`, `strip.gdshaderinc` and the terrain pavement; one branch on `precip` skips it when dry; every preset), **rain splashes** (tiny crowns on a 24 m square of ground ahead of the camera, tilted to the terrain plane, below 40 m AGL, off on uneven ground; strength = `environment/precip`), **wheel spray** from every FDM gear wheel on a wet surface (`environment/wetness`; 0 below 2.5 m/s or when dry, rising with ground speed and wetness, a third on wet grass), a **rooster tail** behind each main wheel from about 20 m/s on a really wet runway, **engine wash** (a propeller at high power standing or slow blows mist back over wet ground; a jet at high thrust a thinner sheet 7 m behind the engine; dust instead on dry grass; strength from thrust against the full static thrust: `thrust_n`, or 0.5 rho A (36 m/s)^2 for a propeller), and **dust** from wheels rolling on dry unpaved ground plus a puff where a main wheel lands there. Paved or not: the runway / taxiway ribbons of `runways.json` plus the airport pavement mask (`terrain/pv` tiles, read on a worker the first time and kept at 8 m; near a runway the ground counts as paved until the tile is in). Particles: GPU, no collision, trails or sub-emitters, so the same on Forward+, Mobile and Compatibility (collision heightfields re-render the scene depth every frame the camera moves and do not exist on Compatibility; random splashes on a flat square look the same as collisions for evenly falling rain). Spray, wash and dust are soft, irregular noise-shaped wisps (`world/ground_fx_textures.gd`: a 2 x 2 atlas, one random frame and a random slow turn per particle, so they read as mist, not round dots) that fade in, grow and fade out; the rooster tail is a thin fan of upright streaks. Sprites are lit by the scene (dark at night, nothing glows; the splash crowns are unshaded and tinted by `environment/light_level` like the rain streaks, `world/rain_splash.gdshader`) and fade within 1-5 m of the camera, and on Forward+ where they meet the ground (proximity fade). No splash is drawn under the fuselage or a wing (two boxes from the gear contacts, collapsed in the splash vertex shader). Floating origin: each emitter keeps its particles in its own frame and moves only by the render shift, its source fed as `emission_shape_offset`. Paused or in a replay no new spray, wash or dust starts; a new flight or F5 clears everything (`TouchdownFx.clear`). Counts (particles alive at full strength: splash / spray per wheel / tail per main wheel / wash per engine / dust per wheel): Low 0 (rings only), Medium 300 / 130 / 0 / 70 / 70, High 600 / 250 / 90 / 140 / 140, Ultra 900 / 350 / 140 / 200 / 200, Max 1000 / 390 / 160 / 220 / 220 (spray is many small faint wisps); Compatibility is held to Medium. Measured on Apple M4 only (MoltenVK GPU timestamps, 1920×1080, C172 wet takeoff roll in rain at VABB, chase view, render scale fixed at the preset's, two interleaved runs, GPU ms off → on): Low +0.2, Medium +0.3, High +1.1, Ultra +2.9, Max +4.3 (Max at 100 % scale; it was +11 with the first, larger Max counts); with the wisp sprites High measured +1.5 (two pairs, runs varied by ±2 ms). The cost is overdraw of soft sprites, so other GPUs should scale with fill rate; CPU time did not change measurably. `tests/debug_ground_fx.tscn` (GFX_SHOT, GFX_OFF, GFX_BENCH) shoots and measures the scenes. Tests: `tests/test_ground_fx.gd`. Not done: tyre smoke stays on CPU particles (one-off bursts on touchdown, no steady cost).

**Ground detail and sun glare:** `world/terrain.gdshader` adds tonal variation at field and hill scale, plus fine grain and a micro-relief normal within about a kilometre, over the 10 m imagery (water excluded). From Medium up it also offsets vertices by a fractal bump (1 m on Medium, 2 m on High and above), full within 1 km and gone by 2 km. The bump is visual only: the flight model still reads the height tiles, and the offset is zero on pavement, roads, rivers, water, and any node whose pavement mask is not bound. `world/sun_glare.gd` / `sun_glare.gdshader` draw a veil, faint starburst and lens ghosts when the sun is in view (not on Low); terrain, cockpit frame and clouds cut it off (depth buffer), and looking toward the sun lowers exposure by up to 20 % (`SkyTime._update_glare`). Tone mapping is AgX (`docs/GRAPHICS-PLAN.md` G1).

**Ground materials and airport pavement** (`tools/26_terrain_textures.py`, `tools/27_pavement.py`; GRAPHICS-PLAN G6): within ~1.2 km the terrain gets tiling CC0 ground materials per WorldCover class (soil on crops, grass, dry scrub, laterite on bare ground, forest floor, gritty built-up ground, sand near the sea, mud in wetlands / mangroves, rock on steep Ghats slopes) at three scales, multiplied under the satellite colour. Aprons, stands and runway / taxiway shoulders are pavement (`world/terrain_pavement.gdshaderinc`): concrete slabs with sealed joints aligned to the runway, asphalt where OSM says so, tyre marks along stand lead-in lines, oil stains where aircraft park, rubber and grime streaks. The pavement tile loads with the road tile (within ~3.6 km). Credits: `CREDITS.md`, `game/world/textures/terrain/SOURCES.md`.

**Roads, rivers and shores** (`tools/20_roads_rivers.py`, `tools/21_shore.py`): the 10-20 m imagery smears roads and creeks, so OSM lines are rasterised into 4 m signed-distance tiles (`terrain/ro/0/`) that `world/terrain.gdshader` draws crisply: asphalt with tyre tracks and white edge / yellow centre lines on primary to tertiary roads (lane lines on motorways and trunks, within ~600 m), plain grey minor roads, tan tracks with ruts, rivers / canals / streams as thin water ribbons with a wet bank. Everything fades out by ~3.3 km; nothing is drawn over runways, aprons or water (bridges stay). Only the level-0 tiles within 3.6 km of the camera are resident (`world/terrain_roads.gd`, `terrain_quadtree.gd`). Narrow roads draw at least ~4.4 m wide; centre lines are solid. Water uses the shore tiles (`terrain/sd/`): shoals fade from turquoise to deep grey-blue over ~100 m, swash lines and wave fronts run toward open coasts (none on rivers, ponds, sheltered water). Not done: mud near river mouths, bathymetry (the DEM is flat at sea level), road dashes, bridges as geometry.

**More sky and surface effects:**
- **Cloud shadows** (`CloudLayer._publish_shadow` publishes coverage noise, wind phase, sun direction and strength as global shader parameters; `terrain.gdshader` darkens ground under a cloud; none under a thick deck, in clear air or at night), a **cirrus layer** (`sky_clouds.gdshader`), **forest floor** darkening under dense tree cover, darker tree crowns underneath, and a **Fresnel cockpit glass** (`aircraft/c172/glass.gdshader`).
- **Aircraft reflection probe** (`aircraft/c172/reflection_rig.gd`, `reflection_policy.gd`; off on Low): a ReflectionProbe above the aircraft captures the real surroundings so glass and paint reflect more than the sky (airframe layer only; box projection off). It re-captures when the picture changed (sun ±2°, 300 m travel, 150 m altitude, cloud / rain / visibility, preset change, 5 s after start) plus periodically (Medium 30 s, High 12 s, Ultra 5 s, Max 3 s; never faster than every 2 s), seeing 2.5 / 4 / 6 / 8 km on Medium / High / Ultra / Max. Resolution is the engine default (128 on Mobile, 256 on Forward+); it cannot be set per preset at run time.
- **Banding:** debanding is on (`project.godot`, `Viewport.use_debanding` in `Graphics.apply_to_scene`) and the sky shader adds about 4 % dither noise.
- **Atmosphere:** `world/atmosphere.gd` is a single-scattering Rayleigh + Mie + ozone sky on a spherical planet, with a twin in `sky_clouds.gdshader` (`atmo_sky`; keep them in step). Overcast, night, rain flashes and city glow still come from `SkyTime`, which also samples it for the fog / haze colour and the sun colour (`Atmosphere.sun_color`: white high, orange at 8°, red-orange at the horizon). After sunset the model keeps the sun on the horizon and fades (`Atmosphere.twilight_gain`); aerosol follows visibility.
- **Auto exposure** (`world/auto_exposure.gd`): Godot's camera auto exposure is Forward+ only, so this is a CPU estimate (sunlit or shaded ground, sky, camera pitch; gentle power law 0.3, clamped 0.8 to 1.5, at most 1.2 at night; smoothed 2.4 s toward darker, 0.9 s toward brighter). Published as `environment/exposure_mult`; off on Low (`ae` in the preset table).

**Trees:**
- Forests are placed from the satellite vegetation index, excluding buildings, roads, runways and water, generated deterministically within the preset's range (1.2 to 3 km) in streamed chunks. Hidden above 1500 m AGL.
- **Species** (`world/tree_species.gd`, one rule for drawing, near meshes and collisions), from the region, the ground height and the ESA WorldCover class of the cell (`TerrainTileCache.worldcover_at`, `TreeSampler` reads `terrain/wc` on its worker threads): forest broadleaf (teak and the semi-evergreen Ghat forest: WorldCover tree cover, most of all in the uplands), coconut palm (Konkan and Kerala lowlands, 1.4 x more round villages and paddies, none in mangroves), acacia scrub (shrubland, bare laterite, the Deccan above 400 m), casuarina / eucalyptus (few; the coast below 30 m), and wide village trees (mango, banyan, peepal, rain tree: three quarters of the trees in built-up areas, most on farmland). Tree positions are unchanged. Heights come in families: forest broadleaf and village trees share one range and one random draw, so only palms, scrub and slim trees can differ from the old four-kind mix (tallest tree still 22 m). Palms have a thinner collision disc, village trees a slightly narrower one than their wide crowns.
- **No trees on runways** (`world/tree_clear.gd`): besides the land-class mask (which already leaves out OSM roads, aeroways and buildings), every runway ribbon in `runways.json` plus 7.5 m of shoulder is kept clear by all three tree paths (drawn, near meshes, collisions).
- **Near meshes** (`world/tree_lod.gd`, `tree_meshes.gd`, `tree_parts.gd`, `tree_mesh.gdshader`, `tree_parts.gdshaderinc`): within the preset's near radius (Max 250 m, Ultra 150, High 120, Medium 90, Low none) trees are procedural meshes built at startup: a dark grey-brown trunk with limbs and crowns of 6 to 9 clumps of alpha-tested leaf cards with gaps between the clumps (sky shows through, the branches show). Coconut palms have a slender, curving, ringed grey-brown trunk (leaf-scar rings drawn in the shader), 20 long narrow feathery fronds folded into a V (young ones up, old ones drooping), the oldest dead and yellow-brown hanging below, and a cluster of coconuts under the crown. Casuarina hangs wispy needle strands in loose tiers. Leaf cards use `game/world/textures/trees/leaf_cards.png` (1024 x 512, drawn by `tools/tree_leaf_cards.py`: broad leaves, acacia leaflets, casuarina needles, grass, a coconut frond, large teak leaves, fern, shrub); their normals lean out of the crown and light comes through them (backlight), so a crown shades as one mass rather than flat paper, and their shadows are dappled. LOD0 (324-642 triangles) adds many small detail cards and twigs that shrink away towards the detail radius (0.4 x the near radius); beyond it an 80 m cell swaps to LOD1 (80-226 triangles; `TreeLod.mesh_lod`, 6 m hysteresis), so the swap shows nothing. Each tree's cards shift a little with its seed, so no two crowns are alike. Off above 450 m AGL.
- **Impostors** (`world/tree_atlas.gd`, `tree_octa.gd` + `tree_octa.gdshaderinc`, `tree_bake.gdshader`, `tree.gdshader`): hemi-octahedral. At startup (and on a preset change) one orthographic render in a private 3D world bakes every species' LOD1 mesh from 8 x 8 directions over the upper hemisphere (the outer ring is 28 side views, the middle looks straight down): albedo + cover (RGBA8) and normal (RG8), with mipmaps, then block-compressed (BC3 / BC5 where the renderer reports S3TC, ETC2 elsewhere; uncompressed if the build has no compressor). Each tree is one quad turned to the camera and cut to its species' box seen from that side (a quarter to a half of the bounding circle, most from above and for slim trees). High and up blend the three frames around the view direction, each sampled where the view ray meets that frame's image plane; Low and Medium take the nearest frame and skip the other projections. So trees look right from above as well as from the side and are lit by the sun through their baked normals. Frame size by preset (`world/tree_quality.gd`): Low 64 px, Medium 72, High and up 96 (frames are drawn at most about 100 px tall at the near radius on a 1080p screen). Atlas memory: 3.3 / 4.2 / 7.5 MB block-compressed, at most 10.5 / 13.3 / 23.6 MB uncompressed (it was 11 MB for every preset before G8). The impostor dithers away over 8 m where the near mesh dithers in (`TreeLod.covered`); a per-pixel dither works on every renderer, where visibility-range fades would act on whole 480 m chunks and are missing on Mobile. Alpha-tested (alpha to coverage under MSAA) so they take the volumetric fog composite. On Compatibility the bake writes sRGB itself (that renderer stores the bake viewport as written). Headless runs get a flat placeholder.
- **Far tree shadows** (`world/tree_shadows.gd`, `tree_shadow.gdshader`): on High and up, impostor trees within 500 m (High), 800 m (Ultra) or 1200 m (Max), and inside the sun's shadow distance, cast shadows from a 28-triangle opaque proxy (icosahedron crown shaped per species on a trunk) drawn in the shadow pass only, a child of each impostor chunk sharing its instance buffer. Opaque proxies skip the alpha test that made impostor shadows cost +9-10 ms at Ultra. Trees inside the near radius (they cast their own) and beyond the proxy radius collapse to nothing in the vertex shader.
- **Canopy shade** (`world/terrain_canopy.gdshaderinc`, in `terrain.gdshader`): beyond the real tree shadows (`canopy_start`: the near radius, or the proxy radius on High and up), the ground under dense tree cover is darkened and greened, open ground beside a forest lies in its shadow on the side away from the sun (two taps of the land-class mask a canopy's shadow length towards the sun), and on High and up (`canopy_detail`) crown-sized bumps are lit on their sun side. Within ~300 m the forest floor gets brown leaf-litter patches and damp hollows. It gives forests depth from the air, also above 1500 m AGL where no trees are drawn. None at night or under overcast.
- **Ground cover** (`world/ground_cover.gd`, `ground_cover_rules.gd`, `ground_cover_meshes.gd`, `ground_cover.gdshader`, `ground_roads.gd`): ferns and bushes under forest canopy, grass tufts on grassland, farmland and wetland edges, sparse dry straw-coloured grass on shrubland, bare laterite and the plateau above 400 m, a few tufts in built-up areas; picked per 1.6 m (High and up) or 2.4 m (Medium) grid point from the WorldCover class and land-class density. Nothing on water, roads, tracks and rivers (the 4 m road tiles, read on worker threads by `GroundRoads`), runway and taxiway ribbons and the apron mask (`GroundSurface`) or `TreeClear` ribbons. MultiMeshes in 24 m cells around the camera, one cell built per frame; cells are placed in world terms and moved with the floating origin, the sway phase comes from each plant's seed, so nothing swims or jumps at an origin shift. Plants shrink away towards the edge of the layer and dry with the season. Radius: Low none, Medium 18 m, High 40, Ultra 50, Max 65; off above 120 m AGL. No shadows cast.
- **Season** (`TreeLook.dryness`, `tree_tint.gdshaderinc`): from `weather/day_of_year`, green from the monsoon (July to October), drying to the end of May. Teak and scrub turn olive and yellow-brown, mango, palms and casuarina hardly change, grass turns towards straw. Every tree also keeps a stable tint, and the crown sways a few centimetres with a phase from its seed (not its position, so nothing jumps when the floating origin shifts).
- **Checks:** `tests/test_tree_look.gd` (species, frame selection, LOD ranges, budgets and atlas memory per preset, runways, origin shifts, curvature, season), `tests/test_ground_cover.gd` (cover kinds, paved ground and water, origin shift, counts per preset, palm and casuarina parts) and `tests/test_trees_buildings.gd`; the look: `tests/showcase_tree_scenes.gd` (`trees_runway`, `trees_palm_grove`, `trees_ghats_2000`, `trees_ghats_8000`, `trees_suburb`, `trees_low_sun`, `trees_night`, `trees_undergrowth`, `trees_grass_runway`, `trees_palm_closeup`, `trees_shadows_low_sun`), shots in `review_screenshots/trees/`. The showcase log line counts ground-cover plants and shadow proxies, and the game prints `TREE ATLAS <px> px, <MB> MB on the GPU` after each bake.

### Replacing the models with your own Blender models

1. Model in Blender in metres, **−Z forward, +Y up, origin at the C172's CG** (about 1.0 m aft of the JSBSim datum; see `mass.empty_cg_m` in `config.json`). Export glTF (`.glb`).
2. Name animated parts `elevator`, `rudder`, `aileron_L`, `aileron_R`, `flap_L`, `flap_R`, `prop`, with pivots on their hinge lines.
3. In the cockpit model, leave a flat panel face with UVs covering 0–1 and a material whose albedo is the panel SubViewport texture (see `Cockpit.build`), so the gauges and clickable knobs keep working.
4. Put the `.glb` files in `models/` of the aircraft folder (`exterior.glb`, `interior.glb`). `AircraftModel` uses them when present (see "Aircraft data: model, cockpit, lights, audio"), else a placeholder airframe sized from `config.json`.

The FlightGear c172p model (GPL) is fine as a private, local stand-in, but do not redistribute it.

### UI font (Fira Sans)

Menus and in-game panels that use `MenuTheme.make()` (start screen, pause, saves, controls overlay) use **Fira Sans** (SIL OFL 1.1), unmodified, as four TTFs in `game/ui/fonts/` with `OFL.txt` and `FONT-NOTICE.txt` (copy and checksums in `third_party/fira-sans/`). `MenuTheme.font("regular" | "medium" | "semibold" | "bold")` returns the cached `FontFile`; `MenuTheme.use_font(control, "semibold", 28)` sets weight and size; `Theme.default_font` is Regular. Design tokens (`ACCENT` `#59BFFF`, `ACCENT_INK`, `DIM`, `PANEL`, `OK` / `WARN` / `BAD`, the `SIZE_*` scale, the 3 px focus ring `MenuTheme.focus_box()`) are in `ui/menu/menu_theme.gd`. The F12 credits and `CREDITS.md` credit the font; `tools/package/make_release.sh` copies `packaging/licenses/fira-sans-OFL.txt` into the release `licenses/` folder. Tests: `tests/test_menu_theme.gd`, `tests/test_attribution.gd`.

**Symbols.** Fira Sans has no triangles, circles, stars, check marks or cog, which the menus use as text (`▶ ◀ ▲ ▼ ● ○ ★ ☆ ✓ ✕ ✗ ⚙`). All four Fira weights list `game/ui/fonts/LibresimSymbols.ttf` as explicit fallback (`MenuTheme.symbols()`): 12 glyphs cut out of DejaVu Sans (about 12 KB, renamed "libresim Symbols" as the Bitstream Vera licence asks; `tools/make_symbols_font.py` rebuilds it; licence and notes in `third_party/dejavu-symbols/`, licence text in the release `licenses/` folder, credited in `CREDITS.md` and on F12). `tests/test_font_glyphs.gd` fails when a character in a start-screen, pause, credits or training script is in neither font. To use a new symbol, add it to `SYMBOLS` in the tool, rebuild and re-run the test. Not covered: two in-flight characters (the radio stack's `⇄`, the attitude gauge's `∩`) use the engine's default font.

## 7. Troubleshooting

| Symptom | Fix |
|---|---|
| `godot: command not found` | Use `~/.local/bin/godot` or add `~/.local/bin` to PATH (section 1) |
| `missing data file: .../terrain/meta.json` | Run the pipeline (section 3) |
| Terrain is a flat green-grey colour | Imagery tiles are missing: run `01b_fetch_imagery.sh`, then `03_imagery_tiles.py` |
| `01b_fetch_imagery.sh` fails partway with HTTP errors | Re-run it; GDAL retries each tile 5 times. The EOX server sometimes rate-limits |
| Aircraft spawns in the wrong place / no runway | Run `tools/09_runways.py` (writes `data/processed/runways.json`) |
| No joystick found on macOS | See "macOS: joysticks and the Thrustmaster pads" |
| No sound | Godot uses PulseAudio/PipeWire; check the system output device |
| Low FPS | Check the F3 overlay. Lower `lod_k` on the Terrain node in `world/flight.tscn` (default 1.6), or turn off `shadow_enabled` on the Sun |
